# 설계 변경 절차 — 영향 범위를 기억이 아니라 조회로

> **왜 이 문서가 생겼나 (2026-07-29)**
>
> 설계는 구현하면서 계속 바뀐다. 문제는 바뀌는 것 자체가 아니라 **바뀐 사실이 원래 결정에
> 되먹임되지 않는 것**이었다. 하루 만에 같은 유형이 네 번 나왔다:
>
> | 무엇 | 증상 |
> |---|---|
> | 이상탐지 | `TASKS.md`는 "코드로 처리된다" — **실제 `.tf`가 없었다** |
> | 예산 절차 | 튜토리얼은 콘솔 클릭을 가르침 — **`budget.tf`가 이미 대체** |
> | 크레딧 만료일 | 두 날짜가 **13일간 공존** (추론이 관측값을 덮어씀) |
> | RDS 전략 | `CONTEXT`는 "RDS 재탈락" — **07-28에 사유 ①이 무효화됐는데 반영 안 됨** |
>
> 마지막 건은 **실제 오답을 유발했다.** 원인이 공통이다: **결정은 `CONTEXT.md`에 살고,
> 재판정은 `eks-migration-log.md`에 산다. 일지는 append-only 시계열이라 "지금 유효한 결정"을
> 알려주지 않는다.** 그래서 CONTEXT만 읽으면 뒤집힌 결정을 유효한 것으로 읽는다.

---

## 원칙

**결정을 바꿀 때 새 기록을 추가하는 것으로 끝내지 않는다. 원본 결정에 되돌아가 표시한다.**

일지에 "재판정했다"고 쓰는 것은 **기록**이지 **반영**이 아니다.
다음 사람(또는 다음 세션의 나)은 일지를 시간순으로 읽지 않는다. 결정 블록을 읽는다.

---

## 결정 메타 줄

드리프트 가능한 **전략 결정**에는 블록 바로 아래 한 줄을 붙인다:

```
> 📌 **D-001** · 상태 `🔄부분무효` · 영향 `path/a.tf`, `docs/b.md`, Stage 2·3 · 재판정 `일지 07-28 "..."`
```

| 필드 | 규칙 |
|---|---|
| **ID** | `D-NNN`, 레포 전체에서 유일 |
| **상태** | `✅유효` / `🔄부분무효` / `❌폐기` / `🚧진행중` 중 하나 |
| **영향** | 이 결정이 바뀌면 흔들리는 **파일 경로**와 Stage. 경로는 실재해야 한다 |
| **재판정** | `🔄부분무효`·`❌폐기`면 **필수** — 어디서 왜 뒤집혔는지 |

> **모든 결정에 붙일 필요는 없다.** "GC는 SerialGC다" 같은 **관측 사실**은 뒤집히면 그냥 틀린 것이라
> 메타가 불필요하다. 붙이는 대상은 **선택이 걸린 전략 결정** — 다르게 고를 수 있었던 것.

## 주장-검증 마커

"X는 코드로 처리된다" 류의 **코드 존재를 전제하는 서술** 옆에 붙인다:

```markdown
- ✅ 이상탐지 — `cost-anomaly.tf`로 처리 <!-- verify: infra/aws-eks/0-bootstrap/cost-anomaly.tf -->
```

경로가 사라지면 CI가 잡는다. **이상탐지 갭을 잡았을 장치가 이것이다.**

> ⚠️ **문법을 설명하는 예시는 꺾쇠 자리표시자(`<경로>`)를 쓴다.** 실제 경로처럼 쓰면 검사기가
> 그 예시를 진짜 마커로 오인한다 — 도입 당시 실제로 이 문서가 검사에 걸렸다.

## 절차 — 설계를 바꿀 때

### 1. 바꾸려는 결정을 먼저 찾는다

```bash
grep -n "📌 \*\*D-" .claude/CONTEXT.md          # 결정 인덱스
```

**없으면 만든다.** 메타 없는 결정을 바꾸는 김에 메타를 붙이는 게 가장 싸다.

### 2. 영향 범위를 읽는다 — 이게 blast radius다

메타 줄의 `영향` 목록이 곧 확인해야 할 곳이다. **기억에 의존하지 않는다.**

목록이 불완전해 보이면 이때 넓힌다:
```bash
grep -rn "<키워드>" .claude/ docs/ infra/ k8s/ --include='*.md'
```

### 3. 영향 범위를 실제로 갱신한다

각 항목을 열어 **뒤집힌 전제 위에 서 있는 서술이 있는지** 본다.
문서가 코드를 앞서지 않게, 코드가 문서를 앞서지 않게.

### 4. 🔴 원본 결정 블록에 되돌아가 표시한다 (가장 자주 빠뜨리는 단계)

- 상태를 갱신한다 (`✅유효` → `🔄부분무효` 등)
- `재판정` 링크를 단다
- **부분 무효면 어느 부분인지 명시한다.** 사유가 여러 개인 결정은 **사유 단위로 판정**한다 —
  "RDS 재탈락" 3개 사유 중 ①만 무효였고 ③은 살아 있었다. 통째로 지웠다면 잘못된 결론에 갔다.

> 💡 **원본을 지우지 말 것.** 취소선·표로 남기고 정정을 병기한다.
> "그때 무엇을 믿었는가"가 사라지면 같은 실수를 다시 한다.

### 5. 검사를 돌린다

```bash
bash .claude/scripts/check-design-integrity.sh
```

`gh pr create` 시 CI(`design-integrity.yml`)가 자동으로 같은 검사를 한다.

## 검사기가 잡는 것 / 못 잡는 것

| ✅ 잡는다 | ❌ 못 잡는다 |
|---|---|
| 영향 경로에 적힌 파일이 사라짐 | 영향 범위 목록 **자체가 불완전**한 것 |
| `verify` 마커의 코드가 사라짐 | 문서 **내용**이 코드와 어긋나는 것 |
| 부분무효인데 재판정 근거 없음 | 두 문서가 **다른 숫자**를 말하는 것 |
| 결정 ID 중복·상태값 오타 | |

**오른쪽 열은 사람이 절차로 막는다.** 검사기는 "경로가 사라졌다" 같은 **기계가 확실히 아는 것**만
본다 — 그 이상을 시키면 오탐이 나고, 오탐이 나는 검사기는 곧 무시된다.

> 오른쪽 열을 줄이려면 **영향 목록을 넓게 적는 습관**이 가장 효과적이다.
> 목록에 있으면 절차 2단계에서 반드시 열어보게 된다.

## 언제 이 절차를 쓰나

| 상황 | 적용 |
|---|---|
| 전략·아키텍처 결정을 바꿈 | ✅ 전 단계 |
| 기각했던 선택지를 다시 채택 | ✅ **특히** — RDS 건이 정확히 이 경우 |
| 코드 파일 삭제·이동 | ✅ 4단계는 생략 가능, 검사기가 경로를 잡음 |
| 일반 기능 구현·버그 수정 | ❌ 불필요 |
| 관측 사실 정정 | ❌ 그냥 고치면 됨 (단, **관측값인지 추론값인지 구분해 적을 것** — 만료일 건의 원인) |
