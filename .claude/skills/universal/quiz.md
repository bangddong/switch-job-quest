# SKILL: Merge Quiz (머지 전 이해도 퀴즈)

**트리거:** 사용자가 "퀴즈", "이해했는지 확인" 요청 시, 또는 규모 큰 PR(신규 도메인·마이그레이션·
아키텍처 변경 포함) 머지 전에 오케스트레이터가 제안

## 목적

diff를 눈으로 읽은 것과 동작을 이해한 것은 다르다. 이 스킬은 **"이해했다고 착각하는 상태"**
(unknown unknowns의 마지막 형태)를 머지 전에 드러낸다. 틀린 문제 = 다시 봐야 할 코드.

이 프로젝트는 학습 목적(이직 준비)이므로, 퀴즈는 검증 장치이자 학습 장치다.

## 절차

1. 리뷰 대상 diff/브랜치의 변경을 파악한다 (`git diff origin/main...HEAD --stat` → 핵심 파일 Read)
2. 3~5문제를 만든다. 문제 유형:
   - **동작 예측**: "이 입력이 들어오면 어떤 응답/상태가 되는가?"
   - **경계 조건**: "X가 null/빈 값/중복이면 어디서 어떻게 처리되는가?"
   - **설계 근거**: "왜 A 대신 B 구조를 택했는가?" (Deviations·결정 테이블 기반)
   - **파급 범위**: "이 변경으로 함께 영향받는 기존 기능은?"
3. 각 문제에 **관련 코드 위치(파일:라인)를 링크**한다
4. 한 번에 한 문제씩 낸다. 답을 받은 뒤 정오답 + 근거 코드를 보여준다
5. 종료 시 요약: 맞은/틀린 문제, 틀린 문제의 재검토 파일 목록

## 규칙

- 답을 먼저 보여주지 않는다 — 사용자가 답한 뒤 공개
- 문제는 diff에 실제로 존재하는 동작만 다룬다 (추측성 문제 금지)
- 사소한 문법·네이밍 문제 금지 — 동작·설계·경계 조건만
- 전부 정답이어도 "재검토 파일 없음"을 명시하고 종료

## 출제 형식 — 이대로 할 것 (07-31 사용자 요청으로 고정)

3a·3b 두 세션에서 검증된 형식이다. **바꾸지 말 것.**

### 1. 재료는 반드시 "이번에 만진 실제 코드/실측"

일반 K8s·AWS 지식 문제를 내지 않는다. **이 레포의 이 diff, 이 세션의 로그**에서만 낸다.
사용자 피드백: *"지금과 같이 실제 코드 베이스의 문제 너무 좋다."*

좋은 문제의 재료:
- 구현하다 발견한 함정 (Blindspot Pass가 찾은 것 포함)
- 실측 로그의 에러 원문·수치
- "왜 A 대신 B를 골랐나" — 결정 테이블·Deviations
- 🔴 **최고의 재료 = "겉보기와 실제가 다른" 지점.** 3b 퀴즈 5문제가 전부 이 유형이었고,
  그래서 전부 틀렸다 — 즉 **정확히 가르쳐야 할 곳**이었다.

### 2. 서술형으로 시작하되, 막히면 즉시 객관식으로 전환

```
1차: 서술형   → "모르겠어"가 나오면 붙들지 말고 바로 가르친다
2차: 객관식   → 방금 가르친 것으로 풀 수 있는 재확인 문제 (보기 3~4개)
```

3a·3b 모두 서술형은 0점이었고 객관식에서 이해가 드러났다.
**서술형 0점은 실패가 아니라 "가르칠 지점을 찾았다"는 신호**로 다룬다.

### 3. 한 번에 한 문제. 답을 받은 즉시 채점 + 근거 코드

여러 문제를 한꺼번에 던지지 않는다. 채점에는 항상 **파일:라인 또는 실측 출력**을 붙인다.

### 4. 오답의 "추론 근거"를 따로 평가한다

답이 틀려도 **소거 근거가 맞았으면 부분정답**으로 인정하고 그렇게 기록한다.
(3b R1 실제 사례: 정답은 틀렸지만 *"가는 우리만 쓰는 태그니까 아니다"* 는 정확했다.)
어디까지 이해했는지가 정오답보다 정보가 많다.

### 5. 가능하면 $0으로 실증해 보인다

말로 설명하는 대신 **그 자리에서 재현**한다. 학습 효과가 다르다.
3b 실제 사례: *"`prevent_destroy` 하나가 destroy 전체를 실패시킨다"* 를
`local_file` 3개짜리 임시 프로젝트로 30초 만에 재현했다(AWS 비용 0).

### 6. 오답은 "교정 → 재확인 문제"로 닫는다

틀린 채로 넘어가지 않는다. 가르친 뒤 **같은 개념을 다른 각도로** 다시 묻고,
맞히면 그때 닫는다. 끝까지 안 잡히면 **마커를 넣지 말고 사용자에게 보고**한다.

### 7. 마지막에 메타 교훈을 뽑는다

개별 문제를 넘어 **문제들의 공통점**을 한 줄로 정리한다.
(3b: *"다섯 문제 전부 겉보기와 실제가 다른 경우였다"* — 개별 사실보다 오래 남는다.)

### 8. 기록은 정직하게

0점이면 0점이라고 적는다. 라운드별 점수 추이(1차 → 2차 → 최종)를 남긴다.
**점수를 좋게 보이려고 다듬지 않는다** — 이 파일의 독자는 6개월 뒤의 본인이고,
그때 필요한 건 "무엇을 몰랐는지"다.

## 종료 조건

전 문제 풀이 완료 + 틀린 문제의 코드 재확인 완료 (또는 사용자가 중단 요청)

## EKS 학습 마일스톤 모드 (`stage/eks-*` 브랜치 — 필수, 예외 없음)

브랜치가 `stage/eks-*`이면 퀴즈는 "제안"이 아니라 **PR 생성 전 필수**다.
`assert-eks-quiz.sh` 훅이 `docs/eks-quizzes/<브랜치>.md` + 통과 마커가 없으면 `gh pr create`를 차단한다.
(CLAUDE.md "학습 설명 의무"가 글로만 있어 실제 누락된 데 대한 기계적 교정.)

일반 Merge Quiz와 다른 점:

1. **재료 = 실측 로그**. diff뿐 아니라 그 세션의 `docs/eks-migration-log.md` 엔트리(실제로 뜬 리소스·
   에러 원문·해결·비용)를 근거로 낸다. 문제는 **"무엇을 / 왜 / 트레이드오프"** 와 개념 이해 중심:
   - "컨트롤플레인 삭제가 오래 걸린 이유는?" / "이 리소스를 지금 안 쓰는데 왜 만들었나?"(OIDC 등)
   - "destroy 후에도 계속 과금될 수 있는 리소스는? 왜 tofu가 안 지우나?"(state 밖 고아)
   - "prod 전환 시 이 학습용 설정이 왜 위험한가?"(공인 IP·SPOT·public endpoint)
2. **기록 필수**. 결과를 `docs/eks-quizzes/<브랜치를 -로>.md`에 남긴다 (예: `stage/eks-1-ecr` →
   `docs/eks-quizzes/stage-eks-1-ecr.md`). 형식:
   ```
   # EKS 학습 퀴즈 — <마일스톤명>
   - 브랜치: stage/eks-1-ecr   · 날짜: YYYY-MM-DD   · HEAD: <sha>

   ## Q1. <질문>
   - 사용자 답: <답>
   - 정오: ✅/❌   - 근거: <파일:라인 / 로그 엔트리 / 리소스>
   ...
   ## 요약
   - 맞음 N / 틀림 M. 틀린 문제 재검토: <항목 또는 "없음">
   ```
3. **통과 마커**. 전 문제 풀이 + 틀린 문제 재검토까지 끝나면 파일 맨 아래에 정확히 `<!-- QUIZ-PASSED -->`를
   적는다. **이 마커가 없으면 훅이 PR을 막는다.** ⚠️ 미완인 채 마커만 먼저 넣지 말 것 — 그건 QA를 chore로
   우회하는 것과 같다.
