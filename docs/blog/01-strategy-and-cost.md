# AWS free tier $200 EKS 실습기 ① — 전략과 비용: 왜 EKS였고, 왜 매번 부수는가

> **시리즈**: ① 전략과 비용 · ② Stage 0~2 VPC·노드그룹·IRSA · ③ Stage 3 EBS와 영속 볼륨 ·
> ④ Stage 4 ALB·HTTPS · ⑤ 프로덕션을 옮기려다 기각한 기록

AWS 신규 계정에 $200 크레딧이 들어왔다. 6개월 뒤 만료된다.

이 글은 그 $200으로 EKS를 배우기로 하고 **두 달 동안 실제로 쓴 돈이 $2.94(1.5%)** 로 끝난 과정의 첫 편이다.
Stage별 명령어는 2편부터 나온다. 이 편은 **그 앞에서 정한 것들** — 무엇을 하지 **않기로** 했는지,
왜 클러스터를 매번 부수는지, 그리고 그 판단의 근거가 된 숫자다.

---

## 1. 먼저 기각한 것: 프로덕션 이관

가장 먼저 든 생각은 *"크레딧 있는 김에 운영 서비스를 AWS로 옮길까"* 였다. 검토하고 **기각했다.**

운영 중인 서비스는 Fly.io에 있고 월 $0다. 이걸 AWS로 옮기면:

| | |
|---|---|
| 방식 | 블루-그린으로 API 도메인을 Fly → AWS ALB로 flip |
| 비용 | ECS Fargate 상시 ≈ **월 $35** (ALB $16 + Fargate 1GB $18 + ECR·데이터 $2) |
| 크레딧 수명 | $200 ÷ $35 = **5.7개월** |

숫자를 적고 나니 답이 나왔다. **6개월 뒤에 월 $35 청구서가 시작된다.** 이건 문제를 없앤 게 아니라
**이연한 것**이다. 애초에 이 프로젝트의 출발점이 *"월 $5.7짜리 스케일업도 안 쓴다"* 였는데 그 **6배**를
영구 비용으로 떠안는 셈이다.

두 번째 이유가 더 결정적이었다. **$200을 상시 운영에 태우면 띄웠다 부수는 실험에 쓸 크레딧이 사라진다.**
prod를 Fly에 두면 같은 $200으로 6개월 내내 실험할 수 있다.

> **결론: prod = Fly($0) 유지. AWS = 학습 전용, 안 쓸 땐 destroy.**

이 결정에 `D-002`라는 ID를 붙이고 *"상시 운영은 기각"* 이라는 제목으로 레포에 박아뒀다.
**왜 ID까지 붙였는지는 5편에서 드러난다** — 두 달 뒤에 내가 이걸 뒤집으려 들었기 때문이다.

## 2. 왜 ECS가 아니라 EKS인가

"컨테이너 오케스트레이션 배우기"가 목표라면 ECS Fargate가 훨씬 싸고 빠르다. 그런데 안 골랐다.

**ECS는 쿠버네티스가 아니다.** AWS 독자 오케스트레이터다.

| | ECS Fargate | **EKS** |
|---|---|---|
| K8s 학습 | ❌ kubectl·pod·manifest·K8s API 전부 없음 | ✅ 정통 |
| 이력서 | 중 | ⭐ 시장에서 K8s >> ECS |
| 복잡도 | 낮음 | 높음 (= 배울 게 많음, 양날) |
| 띄우고 부수기 | 빠름(수 분) | **느림 — up/down 각 ~15분** |
| 세션 비용 | <$1 | $0.3~2 |

개념적 유사물은 있다. Task ≈ Pod, Service ≈ Deployment, TargetGroup ≈ Ingress.
**그런데 실제 스킬은 이전되지 않는다.** `kubectl describe pod`로 이벤트를 읽고, PVC가 왜 Pending인지
StorageClass를 거슬러 올라가는 종류의 경험은 ECS에 없다.

목표가 "돌아가는 서비스"가 아니라 **"K8s를 아는 사람"** 이었으므로 비싸고 느린 쪽을 골랐다.

### 노드는 왜 Fargate 프로파일이 아니라 관리형 노드그룹인가

EKS 안에서도 서버리스(Fargate 프로파일)를 쓸 수 있다. 안 썼다.

> **EKS Fargate는 EBS를 붙이지 못한다** (EFS만 지원).

3편의 목표가 **Postgres StatefulSet + EBS 영구 볼륨**이다. StatefulSet을 제대로 배우려면
블록 스토리지가 필요하고, 그러려면 EC2 노드가 필수다. 학습 목표가 인프라 선택을 결정한 사례다.

## 3. 🔴 제약은 돈이 아니라 시간이다

여기가 이 트랙 전체에서 가장 중요한 숫자다. EKS 요금을 항목으로 분해하면 이렇게 생겼다
(서울 리전, AWS Pricing API 직접 조회):

| 리소스 | 시간당 | 24/7 환산 |
|---|---:|---:|
| **EKS 컨트롤플레인** | **$0.1000** | **$73.0/월** |
| ALB | $0.0225 | $16.4/월 |
| ALB 퍼블릭 IPv4 ×2 AZ | $0.0100 | $7.3/월 |
| LCU 최소 1개 | $0.0080 | $5.8/월 |
| **소계 — 파드가 0개여도 나가는 돈** | **$0.1405** | **$102.6/월** |
| + t4g.medium 노드 ×2 | $0.0832 | |
| + 노드 퍼블릭 IP ×2 | $0.0100 | |
| **합계** | **$0.2337** | **$171/월** |

읽는 법이 중요하다.

```
컨트롤플레인 단독      $0.10 / $0.2337 = 43%
클러스터 골격(파드 0)  $0.1405 / $0.2337 = 60%
```

**"인스턴스를 줄여서 버티기"가 통하지 않는 구조다.** 노드를 전부 0으로 내려도 월 $102가 나간다.
컨트롤플레인은 워크로드와 무관한 고정비이고, **`kubectl scale`로는 끌 수 없다.**

이 산술을 초반에 적어두지 않으면 나중에 *"노드만 줄이면 되지 않나"* 가 반드시 되살아난다.
실제로 두 달 뒤에 되살아났고, 그때 이 표가 그걸 막았다.

## 4. 그래서 destroy-after-use

고정비가 지배한다는 말은 뒤집으면 **"안 켜져 있으면 진짜로 공짜"** 라는 뜻이다.
그래서 규율을 이렇게 잡았다.

> **세션 단위로 `tofu apply` → 작업 → `tofu destroy`. 클러스터는 세션 사이에 존재하지 않는다.**

버퍼(스팟 최고가 + 잡비 10%)를 얹은 실사용 단가:

| 모드 | 시간당 | 용도 |
|---|---:|---|
| t4g.small ×1, ALB 없음 | **$0.13** | 인프라 학습 — nginx 파드로 충분 |
| t4g.medium ×1, ALB 없음 | $0.16 | 실앱 배포 |
| t4g.medium ×2 + ALB | **$0.25** | 풀 토폴로지 |

여기서 나온 결론이 직관과 반대였다.

```
클러스터 완전 재생성   ≈ $0.07
4시간 세션            $0.64
8시간 삽질            $1.28
```

**실패는 사실상 공짜다.** apply가 깨져서 처음부터 다시 세워도 7센트다.
아껴야 할 것은 크레딧이 아니라 **"켜놓고 딴짓하는 시간"** 이었다.

이 관점 전환이 실제로 행동을 바꿨다. 예를 들어 ALB는 세션 내내 켜두지 않고 **마지막 7분만** 켰다.
전체 비용의 4%로 끝났다. 반대로 사람 손이 필요한 단계 — 예컨대 인증서 검증용 DNS 레코드를
콘솔에 넣는 일 — 는 **과금 창 밖으로 뺐다.** 그 대기는 결과적으로 19시간이 걸렸는데,
클러스터를 켜둔 채였다면 $1.9, 이 트랙 **누적 지출의 65%** 였을 것이다. 실제 지출은 $0이다.

> ***사람 손이 들어가는 단계는 과금 창 밖으로 뺀다.*** 이게 이 트랙에서 가장 값이 컸던 한 줄이다.

## 5. 사람 규율로는 못 막는다 — dead man's switch

destroy-after-use의 유일한 실패 모드는 명백하다. **끄는 걸 잊는 것.**

그리고 이건 실제로 일어났다. `destroy`를 백그라운드로 보내고 완료를 확인하지 않은 적이 있다.

```
예상   $0.13
실제   $2.77 ~ 3.14        (21~24배)
원인   destroy가 끝났는지 확인하지 않음 → 15.8시간 가동
```

*"비용은 무엇을 켜느냐가 아니라 어떻게 끄느냐가 정한다."*

그래서 로컬에 리퍼(reaper)를 뒀다. 세 조각이다.

| 조각 | 트리거 | 역할 |
|---|---|---|
| 마커 | `tofu apply` 감지 | 세션 활성 표시 파일 생성 |
| 하트비트 | 작업 턴마다 | *"사람이 아직 있다"* 를 갱신 + 과금 리소스 살아있으면 경고 |
| 리퍼 | 30분마다 | 마커가 있는데 하트비트가 **2시간 stale** → 실제 리소스 확인 후 `tofu destroy` |

작업 중이면 하트비트가 계속 갱신돼 리퍼가 건드리지 않는다. **끝 신호 없이 사라지면**
2시간 뒤 자동으로 정리된다.

여기서 한 번 교정이 있었다. 처음엔 생존 판정을 "EKS 클러스터가 있는가"로만 했는데,
**"EKS는 지워졌는데 RDS는 남은"** 부분 실패 상태에서 마커를 스스로 지워 감시를 끝내버렸다.
RDS가 영구 과금으로 남는 경로다. 판정을 **EKS와 RDS의 OR**로 바꿨다.

> 🔑 **안전장치를 만들 때는 "정상 종료"가 아니라 "부분 실패"를 기준으로 판정 조건을 짠다.**

한계도 적어둔다. macOS가 잠들면 스케줄러가 안 돈다. 깨어날 때 밀린 실행을 따라잡는 구조다.
