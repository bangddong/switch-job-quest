## 1차

### Q1. 램프 중 `daily-api` 재시작 2회가 잡혔다. 중단 조건에 "파드 재시작"이 있는데 왜 중단하지 않았나?
- 사용자 답: "원인을 확인하기 위해"
- 정오: 🟡 **부분정답** — 카운트에 반사하지 않고 원인을 본다는 방향은 맞다. 무엇을 봤는지가 빠졌다
- 정답: **시각을 대조했다.** `finishedAt=2026-09-08T01:37:47Z` 는 램프 시작 전이다
  (기준선 `01:38:49Z` · 스테이지1 `01:39`). 격리 때 daily-api·postgres 가 동시 축출됐고
  daily-api 가 postgres 보다 먼저 떠 startup probe 에 걸려 8초 만에 두 번 죽었다
- 🔑 **`restartCount` 는 누적값이라 "언제"를 담지 않는다.** 램프 끝에 `kubectl get pods` 만 보면
  *"부하가 파드를 죽였다"* 로 읽고 스테이지 4를 무릎으로 잘못 선언했을 것이다
- 근거: `lastState.terminated` 실측 · `Startup probe failed` 이벤트 · 일지 09-08절

### Q2. p95 가 부하와 함께 내려갔다(22.95 → 8.16ms). 왜인가? 왜 판정 규칙의 결함인가?
- 사용자 답: "모르겠어"
- 정오: ❌
- 정답: **JIT 컴파일.** JVM 은 바이트코드를 처음엔 인터프리터로 실행하고, 자주 도는 메서드를
  C1 → C2 로 기계어 컴파일한다. **컴파일 자체가 요청 처리 중에 일어나므로** 스테이지1 의
  22.95ms 에는 콜드 컴파일 비용이 섞여 있다. 즉 *"75 req/s 에서의 응답 시간"* 이 아니라
  *"워밍업 중인 앱의 응답 시간"* 이다
- 결함인 이유: 중단 임계 `스테이지1 p95 × 3` = **68.85ms**. 최고 부하(1200 req/s)의 p95 조차
  17.54ms 로 근처에도 못 갔다 → **이 규칙은 한 번도 발동하지 않았고 앞으로도 안 한다.**
  작동하지 않는 안전장치를 작동한다고 믿는 상태 = *"부재가 성공과 똑같이 생긴"* 실패
- 정황 근거: 엔드포인트당 누적 호출이 1만 회를 넘는 스테이지 3에서 p95 가 평평해진다
- 🟡 **미확인**: JIT 티어 임계값과의 대응은 그럴듯하나 `-XX:+PrintCompilation` 으로 직접 관측 안 함
- 조치: 계획서 §9.3 정정 — 기준선은 **워밍업이 끝난 스테이지(3~4)** 의 p95

### Q3. postgres 측정값은 68Mi 인데 limits 를 512Mi 로 유지했다. 128Mi 로 줄이면 무엇이 문제인가?
- 사용자 답: "메모리 상한과 부딪힘"
- 정오: ✅ **정답**
- 보강: `shared_buffers` 미명시 → 기본 **128MB** → limits 128Mi 는 **버퍼 풀만으로 상한**.
  그리고 68Mi 는 **26행짜리 빈 DB** 의 값이라 *설정된 용량*이 아니라 *지금 만진 페이지의 양*이다
  (§9.5 가 인정한 "같은 행만 조회" 한계의 직접 결과)
- 🔑 #410 의 **거울상**: 그때는 공식이 postgres 를 과하게 키웠고(JVM 하한 448 오적용), 이번엔 과하게 줄인다
- 근거: `k8s/base/postgres-static.yaml` 면제 사유 주석 · 계획서 §10.4

### Q4. cordon 한 노드에 k6 가 어떻게 들어갔나?
- 사용자 답: "모르겠어"
- 정오: ❌
- 정답: **cordon 은 스위치가 아니라 taint 를 붙이는 것**이다 —
  `node.kubernetes.io/unschedulable:NoSchedule`. taint = 노드에 붙는 **거부 표식**,
  toleration = 파드 쪽의 *"나는 이걸 견딘다"* 선언. k6 매니페스트에 정확히 그게 있다
- 그래서 **다른 모든 파드는 막히고 k6 만 들어가는** 상태가 만들어진다 (격리 3중 장치의 2번째)
- 몰랐으면: toleration 없이 nodeSelector 만 걸면 **k6 가 과금 중에 영원히 Pending** 에 갇히고,
  원인이 *"내가 방금 cordon 으로 건 taint"* 라는 걸 찾기까지 nodeSelector·라벨·자원을 다 뒤진다
- 근거: `k8s/loadtest/k6.yaml:116-119`

### Q5. `dropped_iterations` 와 `http_req_failed` 는 각각 무엇의 실패인가?
- 사용자 답: "모르겠어"
- 정오: ❌
- 정답: `http_req_failed` = **서버**가 에러 반환 / `dropped_iterations` = **생성기**가 목표 RPS 미달
- 🔑 **요청을 안 보내면 에러도 안 난다.** 누락분은 `http_req_failed` 의 분모에 들어가지도 않으므로
  그것만 보면 **완벽한 성공으로 보인다.** 09-06 closed loop 실패의 정체가 이것이고,
  스테이지 5a 에서 실제 재현됐다 — 실패 **0/71,616** 인데 dropped **129**
- 근거: 계획서 §9.2 판정표 · 5a/5c 실측

## 2차 (재확인)

### R1. 워밍업 구간을 어떻게 다뤄야 하나?
- 사용자 답: "C. k6에서 제공해주는 warmup을 사용한다"
- 정오: 🟡 **부분정답** — 방향(분리해야 한다)은 맞다. **수단이 사실과 다르다**
- 정정: **k6 에 `warmup` 기능은 없다.** `loadgen.yaml` 의 `warmup` 은 **우리가 쓴 셸 스크립트**로
  엔드포인트당 **1회씩** 호출하며, 목적도 JIT 이 아니라 **Metaspace**(밟은 코드 경로로 자란다)다
- k6 로 만들려면 `ramping-arrival-rate`(메트릭 합산 문제) / 시나리오 2개+`startTime`(태그+
  `handleSummary()` 직접 작성 필요) / 별도 실행 후 폐기(시간=비용) 중 택해 **직접 조립**해야 한다
- 🔑 **가장 싼 정답은 "워밍업 추가"가 아니라 "스테이지1 을 기준선에서 빼는 것"** 이었다 —
  램프가 이미 워밍업을 포함하므로 **추가 과금 0** 으로 고쳐진다(§9.3 정정본이 그것)
- 근거: `k8s/loadtest/loadgen.yaml:53-60` · `k6.yaml` scenarios 블록 · 누적 호출 수 계산

### R2. `drain` 은 `cordon` 과 무엇이 다른가? 왜 drain 을 안 썼나?
- 사용자 답: "둘 다 뭔지 몰라..."
- 정오: ❌ (미학습 → 교육 후 R2' 로 재확인)
- 정답: **`drain` = `cordon` + 기존 파드 전부 축출.** cordon 은 taint 만 붙이고 **기존 파드는 그대로 둔다**
  (그래서 cordon 직후에도 daily-api·postgres 가 6-80 에 남아 있었다)
- drain 을 안 쓴 이유: drain 은 노드를 **완전히** 비우는 도구인데 우리는 **측정 대상 4종만** 옮기려 했다.
  DaemonSet(`aws-node`·`kube-proxy`·`ebs-csi-node`)은 설계상 노드마다 하나라 옮길 곳이 없고
  `--ignore-daemonsets` 플래그를 매번 요구한다. 시스템 **Deployment** 까지 옮기면
  **나머지 노드의 시스템 부담이 달라져 L-47 의 2노드 판정이 오염된다**
- 대가: `kubectl delete pod` 는 Eviction API 가 아니라 **PDB 를 존중하지 않는다**.
  이 클러스터엔 PDB 가 없어 무해했다(QA 확인). 🟡 세션 중 `kubectl get pdb` 재확인은 안 함
- 근거: `k8s/loadtest/pin-loadgen-node.sh` ③단계 주석 · 격리 실행 로그

### R2'. drain 이 `postgres-0` 을 내보냈을 때 새 노드에서 뜨려면 무엇이 성립해야 하나?
- 사용자 답: "같은 네트워크 위에 있어야한다?"
- 정오: 🟡 **부분정답** — 국소성 제약이 있다는 감각은 맞다. 걸리는 것은 **네트워크가 아니라 AZ** 다
- 정답: **EBS 볼륨은 만들어진 AZ 를 벗어나지 못한다.** `2a` 볼륨은 `2a` 인스턴스에만 붙는다 —
  물리적으로 다른 건물의 디스크이기 때문이다. `2a`·`2c` 는 **같은 VPC 라 네트워크로는 통하는데도**
  볼륨은 못 붙는다. 여기가 "네트워크"와 갈리는 지점
- 추가 제약: `accessModes: ["ReadWriteOnce"]` → 한 번에 한 노드. detach 완료 후에야 attach
- 강제 수단: PV 의 `nodeAffinity` 가 `topology.kubernetes.io/zone` 으로 못 박아
  **스케줄러가 애초에 다른 AZ 로 안 보낸다.** 갈 노드가 없으면 **Pending 영구 정지**
- 이번에 문제가 안 된 이유: `nodes.tf` 가 **모든 노드를 단일 AZ 서브넷에 고정** — 3대 전부 `2a`.
  실측으로 `postgres-0` 이 `6-80` → `12-6` 이동 후 정상 기동
- 근거: `postgres-static.yaml` nodeAffinity · `accessModes`(72행) · `nodes.tf` AZ 고정 주석

### R3. 스테이지 5a 의 p95 47.48ms 는 서버가 느려진 증거인가?
- 사용자 답: "JIT ? 웜업 이후인가 ? 빨라진거지"
- 정오: ❌ — JIT 을 떠올린 연결은 좋으나 **방향이 반대**다. JIT 은 빨라지게 하는 요인이고,
  스테이지 5 쯤이면 워밍업은 한참 끝났다(엔드포인트당 누적 **46,502회**)
- 정답: **아니다.** 같은 요약에 `dropped_iterations=129` 가 있다 → 생성기가 밀리면 요청이 몰려 나가고
  그 대기가 측정된 응답 시간에 섞인다. **서버 처리 시간과 분리되지 않는다**
- 결정적 근거는 **통제된 재실행**이다 — 부하는 같은데(≈1200 req/s) 생성기 설정만 바꾸니:

  | 회차 | 설정 | req/s | dropped | p95 |
  |---|---|---:|---:|---:|
  | 5a | PREVUS=100 | 1193.31 | 129 | **47.48ms** |
  | 5b | PREVUS=100 | 1199.14 | 12 | 15.01ms |
  | 5c | PREVUS=800 | 1199.47 | **0** | **17.54ms** |

  서버는 아무것도 안 바뀌었다 → **47.48ms 는 서버의 성질이 아니었다**
- 몰랐으면: 교과서적 무릎으로 읽고 스테이지 4를 확정 → `daily-api` W_peak 을 434 대신 **362Mi**
  로 **72Mi 낮게** 잡았을 것이고, 무엇보다 *"무릎을 찾았다"* 는 **잘못된 확신**으로 끝났을 것이다
  (실제 결론은 *"포화시키지 못해 W_peak 이 하한"* — 다음 판단이 완전히 달라진다)
- ⚠️ 정직하게: 5a·5b 는 **같은 설정인데 dropped 가 129 vs 12** 로 갈렸다. 편차가 커서
  *"VU 사전할당이 원인"* 이라 단정하지 않는다. 확인된 것은 800 에서 0 이 나왔다는 사실뿐
- 근거: 5a/5b/5c k6 요약 실측 · 계획서 §9.2
