## Q1. requests vs 실사용 — 스케줄러는 어느 쪽을 보나

`requests: 512Mi` 인데 cgroup 실사용은 337Mi 였다. 스케줄러의 여유 계산은 어느 숫자를 쓰며,
requests 를 실사용에 맞춰 낮추면 **새로 생기는 위험**은?

**답: B (1차 정답)** — 스케줄러는 **requests 만** 본다(실사용을 아예 모른다). 낮추면 파드가 더
촘촘히 들어가지만, 실사용이 requests 를 넘으면 노드 메모리가 실제로 부족해져 evict/OOM 이 난다.

**보강 — QoS 클래스가 evict 순서를 정한다:**

| 조건 | QoS | evict 순서 |
|---|---|---|
| requests 없음 (ESO 3파드) | BestEffort | **1순위** |
| requests < limits (앱 전부) | Burstable | 2순위 — **requests 초과분이 클수록 먼저** |
| requests == limits | Guaranteed | 마지막 |

requests 를 384Mi 로 낮추고 실사용이 450Mi 가 되면 그 파드는 "약속보다 66Mi 더 쓰는 놈" 이 되어
evict 우선순위가 올라간다. 지금(512 요청 / 337 사용)은 반대로 여유를 깔고 있다.

🔑 그리고 evict 된 증상은 **"용량 부족"** 으로 보인다 → 원인을 노드 크기에서 찾게 된다.
그래서 일지에 *"부하 측정 없이 줄이는 것 금지"* 로 못 박았다.

## Q2. C-5 검증에서 ②와 ⑤는 왜 필요한가

④(정책 후 postgres→ai 타임아웃) 하나만으로 "막혔다" 를 증명할 수 없는 이유는?

**답: B (1차 정답)**

**②가 없을 때 통과하는 가짜 정책**: ai-api 미기동 · Service 셀렉터 오타로 엔드포인트 없음 ·
DNS 실패 — 전부 ④에서 타임아웃이 난다. *"막혔다"* 와 *"애초에 닿은 적 없다"* 가 구별 불가.
②는 도달성·DNS·셀렉터·`wget` 존재를 한 번에 확정한다.

**⑤가 없을 때 통과하는 가짜 정책**:

```yaml
spec:
  podSelector: {}      # 네임스페이스 전체
  policyTypes: [Ingress]
  ingress: []          # 아무도 못 들어옴
```

전면 차단이라 ④를 당연히 통과한다. 그런데 **Stage C 완료 기준(daily→ai 왕복)을 정면으로 깬다.**

> 🔑 **차단 검사는 "막혔다" 가 아니라 "막을 것만 막았다" 를 봐야 한다.**
> 부정 검사 하나는 항상 과잉차단과 구별되지 않는다.

## Q3. 세션 마커가 안 생긴 것이 왜 "apply 차단" 보다 나쁜가

```bash
date … | tee … && nohup tofu apply -auto-approve /tmp/stagec.tfplan > /tmp/apply3.log 2>&1 &
```

훅 앵커 `(^|[;&|(]|&&|\|\|)[[:space:]]*tofu[[:space:]]+apply` 는 구분자 뒤에 `tofu` 가 **바로**
와야 한다. `nohup` 이 끼어 매칭 실패 → 마커 미생성.

**답: B (1차 정답)** — apply 는 정상 진행하고 경고도 없다. 조용히 꺼지는 것은 **dead man's switch 뿐**이다.

**코드로 확인** — C 가 틀린 이유:

```
.claude/scripts/eks-reaper.sh:55
[ -f "$MARKER" ] || exit 0
```

마커가 없으면 리퍼는 **AWS 를 조회조차 안 하고 즉시 종료**한다. 클러스터 생존 여부와 무관하다.

**우회를 일으키는 접두사가 전부 흔한 관용구다**: `nohup` · `time` · `timeout 600` · `env X=1` · `stdbuf`.
종전 회귀 테스트는 `cd x && tofu apply` 만 확인했고 **래퍼는 한 건도 없었다.**

🔑 **하네스 동결 규칙의 해제 조건에 해당한다** — 이론적 구멍이 아니라 실제 과금 세션에서
안전장치가 꺼진 채로 돌았다.

## Q4. 🔴 노드를 늘릴 때 EC2 요금 말고 무엇이 더 붙나 — **출제자 오답**

**의도한 답**: B (공인 IPv4, 노드당 $0.005/h)
**응시자 답**: A (루트 EBS 볼륨)
**판정: 응시자가 옳았다. 출제자의 비용 모델이 루트 EBS 를 빠뜨리고 있었다.**

`nodes.tf` 에 `disk_size` 가 없다 → EKS 관리형 노드그룹 **기본 20 GiB** 가 노드마다 붙는다
(🟡 문서 기본값. 노드가 이미 destroy 돼 이번 세션엔 실측 못 함 — 다음 세션 1회 조회로 확정할 것).

```
노드 1대의 진짜 한계비용
  EC2 $0.0208 + 공인IPv4 $0.0050 + 루트EBS $0.0025 = $0.0283/h
```

**세션 정산도 정정됐다**: ~~33m06s × $0.1790/h = $0.0987~~ → **× $0.1865/h = $0.1029**.

### 🔑 이 문항의 진짜 교훈 — 정정할 때마다 다른 항목을 빠뜨렸다

| 시점 | per-node 비용 서술 | 빠뜨린 것 |
|---|---|---|
| D-009 (08-31 이전) | `+$0.026/h (EC2 $0.0208 + IPv4 $0.005)` | 루트 EBS |
| 08-31 "정정" | *"2×small = 1×medium 동일"* | **IPv4 하나 더** |
| 09-03 "재정정" (#407) | `$0.0258/h` | **루트 EBS** |
| 09-04 (이 퀴즈) | **`$0.0283/h`** | — |

**D-009 가 오히려 가장 정확했고, 그걸 고친다며 두 번 더 틀렸다.**
정정은 원본보다 신뢰를 더 받는데("검증됨" 딱지가 붙는다) 검증 깊이는 오히려 얕았다.
📌 08-31 세션에서도 **사용자 질문이 계획서 오류를 찾아냈다**. 같은 일이 반복됐다.

## Q5. 추정이 정확했으니 낙관 기준으로 가도 됐던 것 아닌가

낙관 추정(노드B 1245Mi)이 실측(1261Mi)과 **16Mi** 차로 맞았다.
그럼 3대는 과했던 것 아닌가?

**답: B (1차 정답)** — 추정이 맞은 건 결과론이다. 결정 시점엔 그 정확도를 알 수 없었다.

**보강 — 이번엔 추정이 정확했는데도 낙관 기준은 틀린 답을 냈다:**

| | 결과 |
|---|---|
| 낙관 **숫자** (B 1245Mi) | ✅ 거의 정확 (실측 1261) |
| 낙관 **가정으로 내린 결론** (2대면 된다) | 🔴 **틀림** — 실측 대입 시 `daily-api` Pending |

```
실측값을 2노드에 대입 (A 959 · B 1261, LeastAllocated)
  postgres  256 → B(1005)   core-api 512 → B(493)
  ai-api    512 → A(447)    daily-api 512 → A 447 · B 493 둘 다 부족 = Pending
```

🔑 **추정을 잘한 것이 결정을 구하지 못했다.** 낙관 시나리오는 애초에 *"순서에 따라 갈린다"* 였고,
갈리는 결정은 이미 안전하지 않다. 숫자가 정확해도 그 사실은 안 바뀐다.

> **비관 기준의 가치는 "틀릴 여지를 결론에서 제거하는 것" 이지 추정 정확도가 아니다.**

C(측정될 때까지 착수 연기)가 틀린 이유도 같다 — 측정하려면 클러스터를 띄워야 하고, 그건
**과금 중에 판단하겠다**는 뜻이다. 이 세션이 33분에 끝난 이유가 정확히 그 반대로 했기 때문이다
(08-31 은 과금 중에 진단해서 51분을 썼다).
