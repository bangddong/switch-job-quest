## Q1. `show -json | grep -c '"aws_db_instance"'` 가 in-cluster 인데 왜 `1` 을 냈나

- 사용자 답: "모르겠어" → 가르침
- 정오: — (1차 미응답)

**핵심**: `tofu show -json` 은 절(section)이 여럿이고 `grep` 은 그걸 구분 못 한다.

```
resource_changes  aws_db_instance: 0    ← 이번에 실제로 만드는 것
planned_values    aws_db_instance: 0    ← 끝나면 존재할 것
configuration     aws_db_instance: 1    ← 코드에 적힌 선언 (count=0 이어도 실린다)
```

`count = 0` 은 *"만들지 마라"* 지 *"선언이 사라진다"* 가 아니다.
→ 그 grep 이 답한 질문은 **"무엇을 만드는가"가 아니라 "무엇을 선언해뒀는가"** 였다.

- 근거: 오늘 `ruby -rjson` 으로 `/tmp/plan.json` 절별 계수 · `variables.db_mode = "in-cluster"` ·
  apply 결과 29개에 RDS 없음
- 손해: 따랐다면 `-var db_mode=rds` → **RDS 실수 기동 $0.025/hr**
- 🔑 이 검사는 *"개수는 db_mode 를 구분 못 한다"* 를 고치려 도입한 **대체 검사**였다.
  대체품이 같은 병에 걸렸다.

### Q1-2 (재확인, 다른 각도) — 고아 EBS 검사의 두 필터

- 사용자 답: "EBS 는 데이터 영속을 위해 남겨놔야 함. 그래서 고아에 포함시키면 안돼"
- 정오: **부분 정답** — 핵심(`Persistent` 태그 제외의 이유)은 정확히 짚음.
  `status=available` 축은 **출제가 잘못 겨냥했다**(teardown 직후엔 `in-use` 볼륨이 없어 차이가 거의 없다).
  → 출제자 실수를 기록에 남긴다. 공교롭게 Q1 과 같은 유형의 실수였다.
- 근거: `docs/eks-session-sop.md` §9 · §9b · `infra/aws-eks/PERSISTENT-RESOURCES.md`
- 핵심: §9(고아, 합격=0건)와 §9b(영속 인벤토리, 합격=원장과 일치)는 **반대 방향 검사**다.
  옛 쿼리는 필터가 없어 매 세션 영속 볼륨을 고아로 신고했다 →
  **매번 실패하는 검사는 곧 눈으로 넘기게 되고, 그때부터 진짜 고아도 안 보인다.**

## Q2. 데이터는 살아남는데 비밀번호만 안 맞는 이유

- 사용자 답: "DB 가 있는 레이어와 패스워드가 있는 레이어가 서로 달라, 패스워드가 부쉈던 이전 패스워드를 그대로 물고 있었다"
- 정오: **✅ 정답** (레이어 분리가 핵심. 보강한 것은 *왜 볼륨이 옛 값을 놓지 않는가*)

**메커니즘**: postgres 이미지는 `POSTGRES_PASSWORD` 를 **`initdb` 시점에만** 읽는다.
데이터 디렉터리가 이미 있으면 `Skipping initialization` 을 찍고 **환경변수를 읽지도 않는다.**
→ 비밀번호 해시가 **볼륨 안에 눌러앉는다.**

```
볼륨    → initdb 때 구운 옛 비밀번호   (0-bootstrap 소유, destroy 안 됨)
tfstate → 재apply 가 만든 새 비밀번호  (2-cluster 소유, destroy 됨)
앱      → FATAL: password authentication failed for user "devquest"
```

- 해결: `random_password.postgres_master` 를 `0-bootstrap` 으로 이동(#373, 원장 L-14).
  **볼륨과 수명이 같아야 하는 것은 볼륨과 같은 레이어에 둔다.**
- 오늘 실측: 동기화 **전에** 파드 IP 로 `select 1` → **`1`**. 즉 이제 무행동 = 정상 상태.
- 참고: `ignore_changes = all` 로는 못 고친다 — destroy 가 state 에서 리소스를 지우면 무시할 대상이 없다.

## Q3. ai-api 예약 412.8Mi vs 실측 175Mi — 왜 다른가

- 사용자 답: "모르겠어" → 가르침
- 정오: — (1차 미응답)

**핵심**: `MaxRAMPercentage` · `MaxMetaspaceSize` · `ReservedCodeCacheSize` 는 전부 **천장**이지
약정이 아니다. `Reserved` 도 **가상 주소 공간 예약**이라 물리 메모리를 안 쓴다 —
컨테이너 상한이 세는 건 **실제로 올라온 양(resident)** 이다.

```
used       지금 담고 있는 양       ← 오늘 175Mi
committed  OS 에서 받아둔 양
max        여기까지만 허용         ← 우리가 더한 412.8Mi
```

- 실측 근거: `tr "\0" " " < /proc/1/cmdline` 로 컨테이너 안 실제 명령 확인.
  플래그는 env 가 아니라 **이미지 ENTRYPOINT 에 구워져 있다**(`JAVA_TOOL_OPTIONS`·`JAVA_OPTS` 빈 값).
- **위험은 가짜가 아니라 조건부다**: 🔴 셋이 동시에 천장에 닿으면 나머지 몫이 35.2Mi 뿐 →
  OOMKill. ⚪ **그 상황이 오는지는 미확인** — 부하를 안 걸었고 `jcmd` 부재(슬림 JRE)로
  풀별 분해도 못 봤다. 조건은 *"metaspace 가 160 캡에 접근하면"*.

### Q3-2 (재확인, 다른 각도) — 스케줄러는 requests 를 보나 실사용을 보나

- 사용자 답: "실제로 쓰고 있던 양"
- 정오: **❌ 오답** — 정답은 **선언된 `requests`**
- 추론 근거 평가: *"실제로 비어 있는 걸 봐야 정확하다"* 는 자연스러운 직관.
  틀린 이유는 정확성이 아니라 **시점** 이다.

**왜 requests 인가**
① 배치 시점의 실사용은 0 에 가깝다(오늘 core-api 기동 19.21초, 이후로도 계속 자란다).
   실사용 기준이면 **갓 만든 파드는 늘 "가벼운 파드"** 로 보여 몰아넣게 되고 몇 분 뒤 같이 터진다.
② `requests` 는 측정이 아니라 **예약석**이다. 지금 안 써도 남에게 안 준다.

**오늘 데이터로 확인되는 반사실**:
```
실사용 835Mi < 노드 1대 allocatable 1365Mi  → 실사용 기준이면 4개를 한 노드에 올렸을 것
그런데 09-08 부하 실측 기준:
  앱 1118Mi (408+434+208+68) + 시스템 406Mi = 1524Mi  >  1365Mi   → 부하 시 넘친다
```
스케줄러가 `requests` 를 보기 때문에 오늘 2:2 로 갈렸고 그 사고가 안 났다.

- 근거: `kubectl describe node` 의 `1142Mi (83%)` 는 **실사용이 아니라 requests 합**
  (같은 시점 실사용은 400Mi 남짓) · `allocatable = 1397828Ki` · `kubectl get pods -o wide`

### Q3-3 (따름정리) — requests 를 실사용에 맞춰 낮추면 안 되는 이유

- 사용자 답: "앱이 기동하면서 메모리를 더 먹을 수 있고, OOME 로 인한 프로세스 킬은 로그가 남지 않아 추적이 힘들다"
- 정오: **✅ 정답** (두 축 모두 짚음)

보강 2건:
① **먼저 오는 건 OOMKill 이 아니라 축출(eviction)** 이다. kubelet 은 **requests 초과분**을 기준으로
   쫓아낼 파드를 고른다 → 175Mi 로 낮추고 208Mi 를 쓰면 축출 1순위. 320Mi 면 약속 안쪽이라 보호받는다.
   **`requests` 는 신고이자 방패다. 딱 맞춰 신고하면 방패가 사라진다.**
② **OOMKill ≠ OutOfMemoryError**

   | | 누가 죽이나 | 흔적 |
   |---|---|---|
   | **OOMKill** (Exit 137) | 컨테이너 상한 초과 → 커널 SIGKILL | **없음** (스택트레이스·GC 로그 flush 안 됨) |
   | `java.lang.OutOfMemoryError` | JVM 이 힙 부족을 감지 → 예외 | 스택트레이스·힙덤프 |

   ai-api 가 무서운 쪽은 앞이다. 힙 상한(156.8Mi)이 컨테이너 상한(448Mi)보다 훨씬 낮아
   **JVM 은 부족을 느끼지 못하고**, 넘치는 건 metaspace·code cache·네이티브라
   **예외를 던질 기회 없이 커널이 먼저 죽인다.**
