## Q1. 동기화 전 `psql -h 127.0.0.1`이 성공한 이유는? 이 실수의 일반형은?

- **사용자 답**: "`-h` 명령어로 두면 무조건 성공함. trust이기 때문"
- **정오**: △ **절반**
- **근거**: `$PGDATA/pg_hba.conf` 실측
  ```
  host  all all 127.0.0.1/32   trust           ← 이 줄만 trust
  host  all all all            scram-sha-256   ← 파드 IP는 여기 걸린다
  ```
- **맞은 것**: `trust`라서 성공한 것이 맞다.
- **틀린 것**: *"`-h`면 무조건 성공"* 은 아니다. 파드 IP(`10.0.4.118`)로 붙었더니 **실패**했다
  (`FATAL: password authentication failed`). `-h` 여부가 아니라 **주소가 루프백이냐**가 갈랐다.
- **못 답한 것 (일반형)**: 검사가 **주장보다 헐거운 대리물**을 봤다. 재려던 것은 *"비밀번호가 맞는가"*,
  실제로 잰 것은 *"TCP로 붙는가"*. 그리고 `pg_hba.conf`를 **열어보지 않고 추론**했다 —
  맞는 전제("소켓은 trust")에서 틀린 결론("그러므로 TCP는 검사된다")을 냈다.

## Q2. liveness도 DB를 보게 만들면? 왜 더 나쁜가?

- **사용자 답**: "readiness는 503을 반환하지 않고 응답 자체를 안 하며 kubelet은 타임아웃도 실패로 친다.
  liveness도 DB를 보게 만들면 똑같이 타임아웃이 발생할 것이며 무한 리로드가 발생"
- **정오**: ✅ **정확**
- **근거**: 실측 — DB 정지 시 kubelet 이벤트
  `Readiness probe failed: ... context deadline exceeded (Client.Timeout exceeded while awaiting headers)`,
  `x12 over 102s`. liveness는 같은 기간 실패 0회, `restarts=0`.
- **보강한 개념** (사용자가 후속 질문): probe 3종은 **처방이 다르다**.

  | probe | 묻는 것 | 실패하면 |
  |---|---|---|
  | startup | 부팅이 끝났나 | 나머지 둘을 억제 |
  | liveness | 죽이고 새로 만들어야 하나 | **컨테이너 재시작** |
  | readiness | 트래픽을 줘도 되나 | **엔드포인트에서 제외** (재시작 X) |

  판단 기준은 *"무엇을 검사할까"* 가 아니라 **"실패했을 때 재시작이 답인가?"**
  DB 장애는 재시작으로 못 고친다 → readiness. 데드락은 고칠 수 있다 → liveness.
  **liveness가 의존성을 보면 고치지도 못하면서 전 파드를 동시에 죽여 장애를 증폭한다.**

## Q3. postgres 비밀번호를 왜 `0-bootstrap`으로 옮겼나? `ignore_changes` 안은 왜 기각됐나?

- **사용자 답**: "2-cluster에 있으면 … 재기동 시에도 이전 패스워드를 바라보기 때문에
  bootstrap에 두고 **destroy 시 완전 소각**되게 해야 하기 때문"
- **정오**: ❌ **방향이 반대**
- **근거**: `infra/aws-eks/0-bootstrap/postgres-password.tf:41` — `lifecycle { prevent_destroy = true }`
- **정정**: `0-bootstrap`에 둔 이유는 destroy 때 **살아남게** 하려는 것이다(소각 반대).
  기전: postgres 이미지는 `POSTGRES_PASSWORD`를 **`initdb` 때만** 쓴다 → 영속 볼륨에 데이터가
  이미 있으면 **읽지도 않고** 옛 해시를 유지한다. 비밀번호가 `2-cluster`에 있으면 destroy 때
  state에서 사라지고 다음 apply에 **새 값**이 생겨 볼륨과 갈라진다.
  → 원칙: **볼륨과 수명이 같아야 하는 것은 볼륨과 같은 레이어에 둔다.**
- **`ignore_changes` 기각 이유**: `ignore_changes`는 *state에 있는 값*과 설정을 비교해 diff를 무시한다.
  **destroy가 state에서 리소스를 지우면 무시할 대상 자체가 없다.** $0 실증:
  apply→재apply는 값 유지, **destroy→재apply는 값이 바뀜**.

## Q4. §9(고아)와 §9b(영속 인벤토리)를 왜 하나로 못 합치나?

- **사용자 답**: "PV는 지우되 PVC는 살려야 하기 때문"
- **정오**: ❌ (그건 teardown 순서 §8의 논점)
- **근거**: `docs/eks-session-sop.md` §9 / §9b, 그리고 08-12 실측(§9 전 항목 0건 / §9b 정확히 1개)
- **정정 — 세 가지가 깨진다**:
  1. **기준 충돌**: 하나는 "0건", 하나는 "정확히 1개". 한 검사가 둘 다 가질 수 없다.
  2. **경보 피로 (실제로 겪음)**: 영속 EBS는 destroy 후 **영원히 `available`이 정상**이다.
     필터 없는 옛 쿼리는 매 세션 "고아 발견"을 띄웠고, 합격 기준이 0건이니 **항상 실패하는 검사**가
     된다 → 눈으로 넘기게 된다 → **그때부터 진짜 고아도 안 보인다.**
  3. **반대 방향 실패를 표현할 수 없다** ← 가장 위험.
     §9b는 볼륨이 **0개여도 실패**다(누가 6개월치 데이터를 지운 것).
     합친 "0건이면 합격" 검사는 그 재난을 **성공으로 판정한다.**

## Q5. 이 레포가 이미 갖고 있는 같은 함정의 가드는? 무엇을 막나?

- **사용자 답**: "ANSI 제어문자가 명령에 들어갔기 때문"
- **정오**: ❌ (ANSI는 별개 사건 — 커밋 메시지가 훅에 걸린 건)
- **근거**: `docs/eks-session-sop.md` §2b의 `[ -z "$SHA" ]`
- **정정**: `SHA`가 비면 `git show "$SHA:$F"`가 `git show ":$F"`가 되는데, `:경로`는
  **인덱스의 파일을 읽는 유효한 git 문법**이다. → ECR과 무관하게 **로컬 워킹트리**를 읽고,
  main엔 수정이 있으니 grep이 성공해 **✅를 낸다.**
  SOP 원문: *"aws 호출이 실패한 상황에서 가장 위험한 방향으로 조용히 통과한다."*
- **오늘의 재발**: `ESO_ROLE=$(tofu output ...)` — apply 미완이라 경고가 났으나 **종료코드 0**,
  경고 본문이 그대로 IRSA 주석에 들어가 ESO가 권한 없이 떴다.
- **🔑 중요한 차이**: ECR의 `[ -z ]` 가드는 **이 버그를 못 막았을 것이다** — 값이 비지 않았고
  에러 메시지가 들어 있었다. 그래서 넣은 것은 **형태 검사**다:
  `case "$ESO_ROLE" in arn:aws:iam::*:role/*)`.
  → **"비었나"보다 "그 모양이 맞나"가 강하다. 값이 있다는 것이 값이 옳다는 뜻은 아니다.**
