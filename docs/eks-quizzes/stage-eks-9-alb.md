## Q1. `ADDRESS` 가 채워진 것이 왜 `target-type: ip` 의 증거인가

- 사용자 답: "target-type 을 올바르게 잡았으니 ADDRESS 가 정확한 주소를 물고 있는 게 아닐까"
- 정오: 🟡 **부분 정답** — 결론은 맞고, **누가 그 칸을 채우는가**가 빠졌다

**관측**
```
$ kubectl apply -f k8s/base/ingress.yaml
ingress.networking.k8s.io/devquest created
$ kubectl get ingress devquest          # 20초 후
devquest  alb  *  k8s-default-devquest-3675af8c03-775497815.ap-northeast-2.elb.amazonaws.com  80  20s
```

**메커니즘** — `ADDRESS` 를 채우는 건 kubectl 이 아니다. `ingress.yaml` 에 호스트명은 한 글자도 없다.

```
① kubectl apply  → Ingress 오브젝트 생성. ADDRESS 빈칸
② LBC 가 발견
③ LBC 가 AWS API → ALB · 리스너 · 타겟그룹 생성, 파드 IP 등록
④ 성공하면 LBC 가 status.loadBalancer.ingress[0].hostname 에 DNS 를 써넣음
⑤ 그게 ADDRESS 칸에 보인다
```

→ **`ADDRESS` 는 LBC 가 ③을 끝냈다는 보고서다.**

`instance` 였다면 **③에서 막힌다**: `instance` 는 ALB 가 **노드의 포트**로 보내는 방식이라
`NodePort` Service 를 요구한다. 우리 Service 는 `ClusterIP` — 노드에 포트를 열지 않는다.
타겟그룹을 못 만들면 ALB 생성이 중단되고 ④에 도달하지 않는다.

```
kubectl apply        → created            ← 성공 메시지는 나온다
kubectl get ingress  → ADDRESS 영원히 빈칸   ← 실패 신호가 에러가 아니라 빈칸이다
kubectl describe     → Events 에만 에러
```

- 손해: 빈칸은 *"아직 진행 중"* 과 구별되지 않는다 → 과금 중에 5분씩 기다리다 콘솔을 열게 된다
- 근거: 오늘 실측 · 타겟 `10.0.3.131:8080`/`10.0.12.186:8082` = `kubectl` 파드 IP 와 일치 ·
  Service 타입은 `k8s/base/*.yaml` ruby 파싱으로 확인
- ⚠️ **미확인**: `instance` 로 두면 실제로 어떤 Events 가 뜨는지 **직접 보지 않았다**(문서 근거)

### Q1-2 (재확인) — `delete ingress` 가 16초 걸린 게 왜 증거인가 / 타임아웃은 왜 거나

- 사용자 답: "바로 반환했으면 오히려 그게 의심 포인트고, 타임아웃이 날 경우면 finalizer 의 순서가 잘못된 게 아닐까"
- 정오: 🟡 **부분 정답** — **전반부가 정확하다**(그게 더 중요한 절반). 후반부는 타임아웃의 목적이
  *진단*보다 **생존**이라는 점이 빠졌다

**관측**
```
$ time kubectl delete ingress --all -A --timeout=180s
ingress.networking.k8s.io "devquest" deleted
  0.17s user  0.06s system  1% cpu  16.033 total      ← CPU 1% = 일한 게 아니라 기다렸다
$ aws elbv2 describe-load-balancers --query 'length(LoadBalancers)'  → 0
```

**메커니즘** — finalizer = *"나를 지우기 전에 처리할 일이 남았다"* 는 표식. 붙어 있으면 K8s 는
`delete` 를 받아도 **즉시 지우지 않고** `deletionTimestamp` 만 찍는다.

```
① kubectl delete → deletionTimestamp. 오브젝트는 아직 있다
② LBC 가 발견  ③ LBC 가 실제 ALB 삭제   ← 16초가 이것
④ LBC 가 finalizer 를 뗀다  ⑤ K8s 가 실제 삭제  ⑥ kubectl 반환
```

🔑 **Q1 과 같은 구조다.** ADDRESS 를 채운 것도, 오브젝트를 지우는 것도 kubectl 이 아니라 LBC 다.
→ 사용자 지적대로 **즉시 반환은 의심 신호**다: finalizer 가 없다는 뜻이고, 오브젝트만 사라지고
**AWS ALB 는 남는다**(월 $16.43 고아).

**타임아웃의 목적은 생존이다** — finalizer 는 "순서를 틀릴" 종류가 아니고, 문제는 **④를 할 주체가
없는 경우**다. LBC 가 죽었거나 evict 됐으면 아무도 처리하지 않아 **영구 hang** 한다.
사람은 Ctrl-C 를 누르지만(→ ALB 고아), **리퍼는 누를 사람이 없다**:
```
리퍼: Ingress 삭제 시도 → 영구 대기 → tofu destroy 에 도달 못 함 → 클러스터가 계속 과금
```
**안전장치를 고치려다 안전장치를 벽돌로 만드는 것.** 그래서 리퍼는 타임아웃을 걸고,
**실패해도 destroy 로 넘어간다**(성패 판정은 `warn_orphan_albs()` 가 따로).

- 근거: `16.033 total` · ALB 0건 · `eks-reaper.sh` `cleanup_k8s_loadbalancers()` ·
  회귀 테스트 케이스 ③(delete 실패에도 destroy 도달)
- ⚠️ **미확인**: LBC 를 죽인 상태의 **진짜 hang** 은 재현하지 않았다(목은 종료코드만 1로 만든 것)

## Q2. `daily-api` 를 0으로 내렸을 때의 503 이 왜 증거인가

- 사용자 답: "둘이 같은 DB 를 바라보고 있으니 응답만으로는 어느 파드에서 오는지 알 수 없음. 따라서 하나를 죽여서 테스트"
- 정오: 🟡 **부분 정답** — **전제를 정확히 짚었다.** 반증이 작동하는 **원리**가 빠졌다

**두 번 실패했다**
```
① 본문 비교 → core 직접 = daily 직접 = ALB 경유   (완전 동일 — 같은 DB 의 같은 행)
② 앱 로그   → (매치 없음 — Spring Boot 기본값은 액세스 로그를 안 찍는다)
```

**원리: 검사의 판정력은 "두 가설이 다른 결과를 예측하는가"에서 온다.**

| 검사 | A(의도대로) 예측 | B(순서 뒤집힘) 예측 | 판정력 |
|---|---|---|:--:|
| 응답 코드 | 200 | **200** | **0** |
| 응답 본문 | Kafka 질문 | **Kafka 질문** | **0** |
| `daily-api` 제거 후 | **503** | **200** | **있다** |

응답 비교는 정보가 부족해서 실패한 게 아니다. **두 가설이 똑같은 답을 예측하기 때문**이다.
그런 검사는 아무리 정확히 수행해도 판정하지 못한다.

```
/api/v1/daily-question  →  503     ← B 가 참이면 core-api 가 받아 200 이 왔을 것이다
/api/v1/companies       →  403     ← core-api 는 살아 있다 = 두 경로가 실제로 갈렸다
복원 후                  →  200
```
🔑 **403 유지가 필요한 절반이다.** 없으면 503 의 원인이 라우팅인지 *"클러스터 전체가 망가진 건지"*
구별되지 않는다.

- 손해: 200 만 보고 ✅ 를 적었다면, 순서가 뒤집혀 **daily-api 가 트래픽을 한 건도 못 받는 상태**를
  "path 라우팅 검증 완료"로 기록한다. Stage 4 의 목적이 **strangler 이관**이라 그 위에 쌓는
  모든 판단이 틀어진다("daily-api 가 잘 받으니 core 쪽 구현을 지우자" 같은)
- 근거: 오늘 실측 · `describe-rules` priority(1:daily-question, 2:/api/v1) ·
  `@RequestMapping` grep(core 10개 · daily 1개, `daily-question` 겹침)
- ⚠️ **미확인**: 순서를 **실제로 뒤집어** 200 이 오는지는 재현하지 않았다(논리적 예측)

### Q2-2 (전이) — `Evicted 0` 은 `requests` 명시의 효과를 증명하나

- 사용자 답: "예측할 수 있는 숫자가 있다면 명시적으로 관리해서 좋다고 생각해. 측정할 수 있는 포인트를 잡았으니 효과가 있었다고 볼 수 있을 것 같아"
- 정오: ❌ **오답** — 다만 **실무 판단으로는 옳은 답**이고, 이 오답이 **내 기록의 과한 주장을 찾아냈다**

Q2 의 기준을 그대로 대면:
```
가설 A  requests 명시가 evict 를 막았다   → 예측: Evicted 0
가설 B  requests 없어도 어차피 안 났다     → 예측: Evicted 0     ← 같다 → 판정력 0
```
그리고 B 가 그럴듯하다:
```
allocatable 1365Mi × 3 = 4095Mi
앱 1568Mi + 시스템 ~1218Mi = 2786Mi  →  여유 ~1300Mi
```
**여유가 큰 노드에서는 BestEffort 도 evict 되지 않는다**(evict 는 압박 상태에서 일어난다).
이 세션은 A 와 B 를 **구별할 조건 자체를 만들지 않았다.**

🔴 **그런데 나는 일지에 *"requests 명시가 유효했다"* 고 적었다 — 과한 주장이고 정정했다.**
#415 F-8 과 같은 형태다(오차가 작은 것을 "모델 검증됨"으로 읽었고, 실제로는 lag 이었다).

**구분해야 하는 두 질문**

| | 질문 | 답 |
|---|---|---|
| **사전 판단** | requests 를 명시해야 하나 | **그렇다** — 사용자 답이 여기에 맞다 |
| **사후 증명** | 명시가 효과를 냈다고 기록해도 되나 | **아니다** — 구별 조건이 없었다 |

명시를 유지하는 근거는 **실패 비용의 비대칭**이다 — 과하면 메모리를 조금 낭비하고, 없으면
BestEffort 가 **조용히** 앱을 밀어낸다. 판단은 옳다. **잘못은 그 판단을 증거로 적은 것이다.**
"명시했다 + evict 안 났다"를 "명시가 막았다"로 이은 것은 인과가 아니라 **동시 발생**이다.

- 조치: 일지의 해당 단락을 정정 — ✅확인(명시해도 문제없었다) / ⚪미확인(필요했는지)로 갈랐다

## 메타 교훈

> **검사의 판정력은 정확도가 아니라 "두 가설이 다른 결과를 예측하는가"에서 온다.**

이번 세션의 네 장면이 전부 같은 축이었다.

| 장면 | 두 가설 | 예측이 갈리나 |
|---|---|:--:|
| ADDRESS 빈칸 | ALB 생성됨 / 실패함 | ✅ 갈린다 → 판정 가능 |
| delete 16초 | finalizer 있음 / 없음 | ✅ 갈린다(즉시 반환 vs 대기) |
| 응답 본문 | 라우팅 정상 / 뒤집힘 | ❌ **같다** → 판정 불가 |
| Evicted 0 | requests 가 막음 / 원래 안 남 | ❌ **같다** → 판정 불가 |

🔑 그리고 **뒤 두 개를 같은 실수로 다루지 못했다.** 응답 본문의 무효는 그 자리에서 알아채
반증 실험으로 갔는데, `Evicted 0` 은 **알아채지 못하고 인과로 적었다.** 같은 원리인데
한 번은 적용하고 한 번은 못 했다 — 원리를 아는 것과 매 장면에서 쓰는 것은 다른 일이다.

📌 09-09 퀴즈의 메타 교훈(*"어떤 숫자가 맞는 답인지는 던진 질문이 정한다"*)의 **작동 가능한 형태**다.
그때는 "질문을 보라"였고, 이번엔 **"두 가설을 세우고 예측이 갈리는지 보라"** 라는 절차가 됐다.
