## Q1. Karpenter 는 무엇을 보고 노드가 더 필요하다고 판단하는가

파드가 생긴 지 1.6초 만에 NodeClaim 이 만들어진 기록을 보여 주고, "노드 CPU 사용률을 본 것인가"를 물었다.

- 사용자 답 (1차): "모르겠어"
- 정오 (1차): ❌

### 해설

**① 무슨 작업 중이었나.** k6 로 초당 200건 부하를 걸어 두고, HPA 가 파드를 늘릴 때 Karpenter 가
어떻게 반응하는지 컨트롤러 로그를 보고 있었다.

**② 무엇이 관측됐나.**

```
14:44:50    파드 생성 → Pending
14:44:51.6  Karpenter: NodeClaim 생성 (요구량 cpu 380m · memory 616Mi)
14:44:54.0  EC2 주문 완료 (t4g.small)
```

**③ 왜 그런가.** Karpenter 가 보는 것은 "스케줄러가 자리를 못 찾은 파드가 있는가" 하나다.

1. 부하가 올라 CPU 사용률이 오른다.
2. HPA 가 사용률을 보고 파드를 하나 더 만든다. 사용률을 보는 주체는 여기까지다.
3. 스케줄러가 새 파드를 놓을 노드를 찾는다. 이때 실제 사용량이 아니라 **요청량(requests)의 합**으로
   계산한다. 요청량은 파드가 "최소 이만큼 필요하다"고 선언한 값이다. 노드에 남은 요청 여유가
   파드 요청량보다 작으면 "배치 불가" 표시를 붙이고 Pending 으로 둔다.
4. Karpenter 는 그 표시가 붙은 파드를 발견하고, 요청량을 더해 그만큼 들어가는 가장 싼 인스턴스를 고른다.

1.6초가 증거다. 사용률 지표는 기본 15초 간격으로 수집되므로 사용률 기반이면 이렇게 빨리
반응할 수 없다. Karpenter 는 파드 상태 변화를 알림으로 받는다.

**④ 안 그랬으면 어땠나.** "노드가 바쁘면 Karpenter 가 알아서 늘려 준다"고 믿게 된다. 실제로는
Pending 파드가 없으면 노드 CPU 가 100% 여도 아무 일도 하지 않는다.

**⑤ 근거.** 일지 2026-10-12 P3 시각표. 15초 수집 간격은 metrics-server 기본값이며 이 세션에서
따로 재지 않았다(미확인).

### Q1-2 (재확인, 다른 각도)

HPA 가 없고 파드 3개가 전부 노드에 올라가 있으며 노드 CPU 가 100% 인 클러스터에서
Karpenter 가 노드를 띄우는가, 띄우게 하려면 무엇이 먼저 일어나야 하는가.

- 사용자 답: "안띄울 것 같아. 스케줄상 3개 올리기로 했고 어쨌든 3개를 다 올렸으니까 ?"
- 정오: ✅ (앞 질문). 뒷 질문(무엇이 먼저 일어나야 하나)은 답하지 않았다.
- 근거: 파드 3개가 전부 배치됐으므로 Pending 이 없고, Karpenter 가 반응할 대상이 없다.
  노드가 늘려면 **자리를 못 찾는 파드가 먼저 생겨야** 한다 — HPA 를 붙이거나 replicas 를 손으로 올려서.

## Q2. 파드 3개가 동시에 Pending 일 때 왜 `t4g.medium` 을 골랐고, 거절당한 뒤 어떻게 됐는가

로그(`requests memory 1640Mi`, `instance-types "t4g.medium"`)를 보여 주고 ① 왜 medium 인가
② AWS 가 거절한 뒤 Karpenter 가 어떻게 행동했을지를 물었다.

- 사용자 답: "파드들의 요청이 small로는 감당되지 않으니 medium을 선택했으나 내 계정은 프리티어라
  만들 수 없었나 ? 기대하는건 거절 당했으나 어떻게든 해결은 해야하니 small로라도 올릴 것 같아"
- 정오: ① ✅ ② ❌ (small 로 다시 시도하지 않았다)

### 해설

**① 무슨 작업 중이었나.** 총량 상한(E2)을 보려고 HPA 를 6 으로 고정해 Pending 파드 3개를
한꺼번에 만들었다. 당시 NodePool 후보는 `t4g.small` 과 `t4g.medium` 둘이었다.

**② 무엇이 관측됐나.**

```
14:50:37.091 computed new nodeclaim(s) to fit pod(s)  {"nodeclaims":1,"pods":3}
14:50:37.102 created nodeclaim  requests {"cpu":"780m","memory":"1640Mi","pods":"6"}  instance-types "t4g.medium"
14:50:39.637 ERROR launching nodeclaim ... InvalidParameterCombination:
             The specified instance type is not eligible for Free Tier.
             (aws-error-code=UnfulfillableCapacity, aws-operation-name=CreateFleet)
```

그 뒤 NodeClaim 은 `Launched=Unknown (FreeTierIneligible)` 로 멈췄고, 10초마다
`cluster is waiting on sync for extended duration` 이 찍혔다. 파드 3개는 2분 40초 동안 Pending 이었다.
HPA 를 9 로 올려 Pending 을 6개 더 만들어도 새 주문은 나오지 않았다.

**③ 왜 그런가.**

- *왜 medium 인가.* Karpenter 는 Pending 파드를 **묶어서** 계산하고, 노드 수가 가장 적게 드는 쪽을
  고른다. 3개의 요청 합 1640Mi 는 `t4g.small` 의 쓸 수 있는 몫(약 1261Mi)을 넘으므로 "한 대에 담는다"는
  계획에서 후보가 medium 하나만 남았다. 로그의 `"nodeclaims":1` 이 그 결정이다.
- *왜 small 로 넘어가지 않았나.* "small 2대"는 **다른 계획**이지 같은 주문서의 다음 후보가 아니다.
  주문서(NodeClaim) 한 장에는 그 계획에 맞는 종류만 적히는데, 이번에는 medium 하나뿐이었다.
  그리고 Karpenter 는 이미 낸 주문서를 "곧 올 노드"로 계산에 넣는다. 주문서가 실패도 성공도 아닌
  상태로 남아 있는 동안에는 그 파드들이 이미 처리된 것으로 보여 새 계획을 세우지 않는다.
  (뒤 문장은 관측된 행동에서 추론한 것이다 — 소스 코드로 확인하지 않았다. 🟡)

**④ 안 그랬으면 어땠나.** "거절당하면 알아서 다른 종류로 간다"고 믿으면 NodePool 후보를 넓게
열어 둔다. 그러면 계정이 띄울 수 없는 종류가 하나만 섞여 있어도 **확장 전체가 멈춘다.** 파드는
Pending 인 채 사람이 주문서를 지워 줄 때까지 기다린다. 부하가 실제로 온 상황이면 장애다.

**⑤ 근거.** 일지 2026-10-12 「계획에 없던 발견 ②」. 수정: `k8s/karpenter/nodepool.yaml` 의 후보를
`t4g.small` 하나로 좁혔다. 이 계정이 medium 을 못 띄운다는 사실은 일지 08-31 (D-010) 에 이미 있었다 —
계획서를 쓸 때 대조하지 않았다.

### Q2-2 (재확인, 다른 각도)

주문서가 멈춰 있는 동안 HPA 를 9 로 올려 Pending 6개를 더 만들었다. `t4g.small` 은 후보에 있고
계정도 띄울 수 있다. Karpenter 가 이 6개를 위해 small 을 주문했는가.

- 사용자 답: "안했을 것 같아. karpenter는 주문서 기반이니까 할 작업이 없다고 생각할 것 같은데?"
- 정오: 결론 ✅ / 이유는 부분정답
- 근거: 새 주문은 나오지 않았다(일지 2026-10-12 「E2 미관측」 — "위 NodeClaim 이 막고 있어 새 계산이 돌지 않았다").
  다만 "할 일이 없다고 판단했다"가 아니다. 로그는 10초마다 `cluster is waiting on sync for extended duration` 이었다 —
  Karpenter 는 자기가 아는 상태와 실제 클러스터가 맞을 때까지 **계산 자체를 시작하지 않는다.** 멈춘 주문서 한 장이
  그 맞춤을 막았고, 그래서 그 주문서와 무관한 파드까지 함께 기다렸다. "판단해서 안 한 것"과 "판단을 못 한 것"의
  차이다: 앞쪽이면 6개는 따로 처리됐어야 한다. (동기화 대기가 원인이라는 것은 로그 문구에서 읽은 것이다. 🟡)

## Q3. 일하던 노드가 지워진 뒤 44초 만에 왜 노드가 다시 필요해졌는가

`HPA 4→3 (14:43:28)` → `Underutilized delete (14:43:36)` → `노드 삭제 (14:44:07)` → `새 NodeClaim (14:44:51)`
기록을 보여 주고 ① 지워진 노드 위의 파드는 어떻게 됐나 ② 44초 사이에 무슨 일이 있었나를 물었다.

- 사용자 답 (1차): "모르겠어"
- 정오 (1차): ❌

### 해설

**① 무슨 작업 중이었나.** 부하(초당 200건)가 아직 걸려 있었다. Karpenter 가 띄운 노드 한 대 위에
core-api 파드 하나가 요청을 받고 있었다.

**② 무엇이 관측됐나.**

```
14:43:28      HPA core-api 4 → 3
14:43:36.405  disrupting node(s)  Underutilized/…: delete: [ip-10-0-1-175…] (savings: $0.02)
14:44:07.975  deleted node
14:44:51.590  found provisionable pod(s)      ← 44초 뒤 다시 Pending
```

**③ 왜 그런가.**

1. HPA 가 파드를 하나 줄이자 관리형 노드에 자리가 하나 났다.
2. Karpenter 는 "내 노드의 파드를 그 빈자리로 보내면 노드 한 대가 필요 없다"고 계산했다. 이것이
   `Underutilized` 다. 절약액은 시간당 $0.02.
3. 쿠버네티스에는 돌고 있는 파드를 그대로 들어 옮기는 기능이 없다. "옮긴다"는 **그 파드를 죽이고,
   Deployment 가 다른 노드에 새 파드를 만든다**는 뜻이다.
4. 새 파드는 콜드 JVM 이다. 같은 요청에 CPU 를 훨씬 많이 쓴다.
5. 평균 CPU 가 다시 올라 HPA 가 3 → 4 로 늘렸다. 그런데 방금 노드를 지웠으므로 자리가 없다 → Pending.
6. Karpenter 가 같은 크기의 노드를 다시 주문했다.

HPA(파드 수) · Karpenter(노드 수) · JVM 워밍업이 서로를 밀어 올리는 고리다.
(4→5 의 인과는 시각의 앞뒤와 5a 에서 잰 콜드 JVM 의 CPU 로 이은 것이다. 그 파드의 CPU 를 그 순간 따로 재지는 않았다. 🟡)

**④ 안 그랬으면 어땠나.** 통합을 "공짜 절약"으로 보게 된다. 실제로는 시간당 $0.02 를 아끼려고
받던 요청을 끊고, 콜드 파드를 하나 만들고, 61초짜리 노드 주문을 한 번 더 치렀다.

**⑤ 근거.** 일지 2026-10-12 「계획에 없던 발견 ①」, `k8s/karpenter/nodepool.yaml` 의 `consolidationPolicy`.
완화책은 이번에 시험하지 않았다(계획서 「이번에 하지 않는 것」).

### Q3-2 (재확인, 다른 각도)

5분 뒤의 `Empty → delete (14:49:22)` 는 왜 노드를 다시 부르지 않았는가.

- 사용자 답: "이전엔 Underutilized였으나 이번 로그는 Empty네. 그러니 cold issue가 없으니 새 pod가 필요없겠지."
- 정오: ✅
- 근거: 빈 노드에는 죽일 파드가 없다. 위 3번(파드를 죽이고 새로 만든다)이 일어나지 않으므로 콜드 JVM 도,
  HPA 의 재확장도 없다. 일지 2026-10-12 P6 (`Empty` 14:49:22.994 → 삭제 14:49:58.102, 이후 새 NodeClaim 없음).

### 사용자 추가 질문 — 1~2번을 더 자세히

- *HPA 가 왜 줄였나.* HPA 는 파드들의 평균 CPU 사용률을 목표치와 비교해 `필요한 수 = 올림(현재 수 × 현재 사용률 ÷ 목표)` 로
  계산한다. 4개가 평균적으로 목표보다 충분히 낮게 쓰면 답이 3 이 된다. 부하는 그대로였으므로 사용률이 내려간 이유는
  파드들이 워밍업을 마쳐 같은 요청을 더 적은 CPU 로 처리하게 된 것으로 본다(그 순간의 사용률을 기록하지 않았다. 🟡).
  줄이기 전 대기 시간은 60초로 줄여 둔 상태였다(`k8s/hpa/` 의 `stabilizationWindowSeconds: 60`, 기본 300초).
- *관리형 노드에 자리가 났다는 말.* 노드마다 파드 요청량을 담을 수 있는 총량이 정해져 있다(small 은 약 1261Mi).
  HPA 가 없앤 파드가 마침 관리형 노드 위에 있었으므로, 그 노드에 파드 한 개 분량(616Mi)의 요청 여유가 생겼다.
- *Karpenter 의 계산.* Karpenter 는 주기적으로 "내 노드를 없앤다면 그 위 파드들이 나머지 노드에 다 들어가는가"를
  가상으로 돌려 본다. 들어가면 그 노드는 없어도 되는 노드다. 직전까지는 빈자리가 없어 답이 "안 들어간다"였는데,
  HPA 가 자리를 하나 만들자 답이 "들어간다"로 바뀌었다. 8초 뒤 삭제를 결정했다.

## Q4. Karpenter 노드가 살아 있는 채 대비 없이 `tofu destroy` 만 치면 생기는 문제 두 가지

돈과 관련된 것 하나, destroy 자체의 성패와 관련된 것 하나를 물었다. 답하기 전에 사용자가
"관리형 노드와 Karpenter 노드의 차이"를 물어 먼저 설명했다(누가 만들고 누가 지우는가, tofu 장부에 있는가).

- 사용자 답: "karpenter 노드는 tofu가 관리하지 않으니 tofu destroy를 실행하더라도 죽지 않음. 따라서 destroy에
  의해 대부분의 파드는 죽었지만 불필요한 리소스가 남는다 ?"
- 정오: 돈 ✅ / destroy 성패 — 답하지 않음 (❌)

### 해설

**① 무슨 작업 중이었나.** 세션을 끝낼 때의 문제다. 이 레포의 종료는 `tofu destroy` 하나로 끝나야 한다 —
사람이 자리에 없을 때 자동 종료 장치(리퍼)가 치는 명령이 그것뿐이기 때문이다.

**② 무엇이 관측됐나.** 어제 destroy 에서 정리 실행기가 찍은 출력:

```
terraform_data.karpenter_cleanup (local-exec): [karpenter-cleanup] Karpenter EC2 없음
terraform_data.karpenter_cleanup (local-exec): [karpenter-cleanup] 인스턴스 프로파일 삭제: devquest-eks_<해시>
terraform_data.karpenter_cleanup (local-exec): [karpenter-cleanup] ✅ 잔존 EC2 0
```

그 뒤 노드 역할 삭제가 성공했다.

**③ 왜 그런가.** tofu 는 장부(state)에 있는 것만 지운다. Karpenter 가 만든 세 가지는 장부에 없다.

- *돈.* EC2 가 주인 없이 남는다. 클러스터가 사라져도 인스턴스는 켜져 있고, `t4g.small` 한 대가 월 약 $20 이다.
- *destroy 실패.* 인스턴스 프로파일은 EC2 에 IAM 역할을 끼워 주는 껍데기다. Karpenter 가 만든 프로파일에
  **우리 노드 역할이 끼워져 있다.** IAM 은 프로파일에 끼워진 역할을 지우지 못하게 한다(`DeleteConflict`).
  노드 역할은 tofu 장부에 있으므로 tofu 는 지우려 하고, 장부에 없는 프로파일 때문에 실패한다.
  destroy 가 중간에 멈추면 그 뒤 순서의 리소스가 남는다.

그래서 삭제 시점에만 도는 실행기를 넣었다(`karpenter-cleanup.tf`). EC2 종료 → 시작 템플릿 삭제 →
프로파일에서 역할을 빼고 프로파일 삭제 순으로 한다.

**④ 안 그랬으면 어땠나.** "destroy 가 끝났으니 과금도 끝났다"고 믿는다. EC2 는 다음 청구서에서야 보인다.
사람이 없는 상황(리퍼)이면 destroy 가 역할 삭제에서 실패한 채 아무도 모른다.

**⑤ 근거.** `infra/aws-eks/2-cluster/karpenter-cleanup.tf:3-8`, `scripts/karpenter-cleanup.sh:54-66`.
⚠️ `DeleteConflict` 는 **어제 실제로 보지 못했다** — 스크립트가 프로파일을 먼저 지웠기 때문이다. IAM 의 문서화된
동작으로 적은 것이다. EC2 가 남는 쪽도 보지 못했다(Q5 에서 다룬다).

### Q4-2 (재확인, 다른 각도)

정리 스크립트를 노드그룹 삭제보다 먼저 돌리면 어떻게 되는가.

- 사용자 답: "Karpenter 컨트롤러가 정리 스크립트에 의해 자기가 관리하는 pod가 죽은지 모르고 다시 살리려 할 것 같아"
- 정오: ✅ (표현 두 군데 교정)
- 근거: 컨트롤러가 살아 있으면 지운 것을 다시 만든다는 핵심이 맞다. 교정 — ① Karpenter 가 관리하는 것은 파드가 아니라
  **노드**다 ② "모르고"가 아니라 Q1 의 경로 그대로다: EC2 가 죽는다 → 그 위 파드를 Deployment 가 다시 만든다 →
  자리가 없어 Pending → Karpenter 가 Pending 을 보고 새 EC2 를 주문한다. 스크립트는 방금 지운 것과 같은 것을 다시 만난다.
  그래서 컨트롤러가 얹힌 노드그룹을 먼저 지운다(`karpenter-cleanup.tf:19-21`, `nodes.tf` 의 `depends_on`).
  이 재생성은 어제 실제로 일으켜 보지 않았다(설계 근거다).

## Q5. destroy 가 성공하고 EC2 가 0대면 "P7 통과: 정리 스크립트가 EC2 를 지운다"고 적어도 되는가

- 사용자 답 (1차): "음 .... 다운타임까지 고려해야 하나 ? EC2에 종료 호출 성공을 보진 않은 것 같은데"
- 정오 (1차): 부분정답 — "무언가를 보지 못했다"는 방향은 맞다. 무엇을 못 봤는지가 빗나갔다
  (종료 호출은 있었고 성공했다. 다만 **부른 주체가 스크립트가 아니었다**). 다운타임은 무관하다 — 전부 지우는 중이다.

### 해설

**① 무슨 작업 중이었나.** 세션 종료. P7 을 보려고 Karpenter 노드 한 대를 일부러 살려 둔 채,
`kubectl` 로 아무것도 정리하지 않고 `tofu destroy` 를 시작했다.

**② 무엇이 관측됐나.**

```
15:58:05  노드그룹 destroy 시작
15:58:40  CloudTrail: 그 EC2 에 종료 호출 — 호출 주체는 Karpenter (앞선 두 번의 통합 삭제와 같은 형태의 세션 이름)
...
[karpenter-cleanup] Karpenter EC2 없음
[karpenter-cleanup] 인스턴스 프로파일 삭제: devquest-eks_<해시>
[karpenter-cleanup] ✅ 잔존 EC2 0
```

**③ 왜 그런가.** EC2 를 지운 것은 스크립트가 아니라 **Karpenter 자신**이었다. 노드그룹 삭제가 시작되고
35초 뒤, 아직 살아 있던 컨트롤러가 자기 노드를 종료했다(왜 그랬는지는 확인하지 못했다 — 그 시각의 컨트롤러
로그를 받지 않았다. ⚪). 스크립트가 돌았을 때는 지울 EC2 가 이미 없었고, 그래서 `Karpenter EC2 없음` 을 찍고
EC2 종료 부분(`karpenter-cleanup.sh:36-41`)을 **건너뛰었다.** 그 코드가 진짜 AWS 를 상대로 돈 적은 한 번도 없다.
모의 실행은 "가짜 `aws` 가 인스턴스 ID 를 돌려주면 종료 명령을 부른다"까지만 보여 준다 — 필터가 실제 Karpenter
인스턴스를 잡는지, 권한이 되는지, 대기가 끝나는지는 보여 주지 않는다.

확인된 것과 아닌 것:

| 주장 | 근거 | 상태 |
|---|---|---|
| destroy 뒤 EC2 가 0대다 | 종료 후 AWS 조회 | ✅ |
| 스크립트가 프로파일을 지워 역할 삭제가 된다 | 실제 출력 + 역할 삭제 성공 | ✅ |
| 스크립트가 **EC2 를** 지운다 | 모의 실행뿐 | ❌ 미검증 |

**④ 안 그랬으면 어땠나.** "EC2 0대 = 스크립트가 지웠다"로 적으면, 다음에 Karpenter 가 먼저 지워 주지 않는
상황(컨트롤러가 죽어 있거나 노드가 여러 대)에서 스크립트가 처음으로 진짜 일을 하게 된다. 거기에 버그가 있으면
EC2 가 남고, 문서에는 "검증됨"이라 적혀 있다. 결과가 같다고 원인이 같지는 않다.

**⑤ 근거.** 일지 2026-10-12 「P7 — EC2 가 destroy 보다 먼저 사라졌다」. 그래서 P7 은 "통과"가 아니라
**조건부**로 적었다(계획서 머리말, README 진행표).

### Q5-2 (재확인, 다른 각도)

다음 세션에서 스크립트의 EC2 종료 부분을 진짜로 검증하려면 destroy 전에 어떤 상태를 만들어야 하는가.

- 사용자 답: "모르겠어"
- 정오: ❌
- 가르친 것: **Karpenter 컨트롤러를 먼저 멈춘다**(`kubectl scale deploy karpenter -n kube-system --replicas=0`).
  Karpenter 노드를 지울 수 있는 주체는 둘뿐이다 — 컨트롤러와 정리 스크립트. 어제는 컨트롤러가 먼저 지웠다.
  컨트롤러를 멈추면 EC2 는 살아 있는데 지울 주체가 없는 상태가 되고, 그 상태로 destroy 를 치면 스크립트가
  그 EC2 를 직접 만나 `EC2 종료: i-…` 를 찍어야 한다. 이 절차는 **아직 실행하지 않았다**(계획서 「이번에 하지 않는 것」).

### Q5-3 (재확인, 또 다른 각도)

컨트롤러를 0개로 줄인 상태에서 Karpenter 노드가 비면 어떻게 되고, 사람이 destroy 없이 자리를 뜨면 돈은 어떻게 되는가.

- 사용자 답: "계속 나갈 것 같은데 ? tofu는 karpenter가 관리하는 노드를 관리하지 않잖아"
- 정오: ✅
- 근거: 빈 노드를 지우는 `Empty` 판정은 컨트롤러가 하는 일이다. 컨트롤러가 없으면 그 판정을 할 주체가 없다.
  tofu 는 그 노드를 장부에 갖고 있지 않고, 애초에 아무도 destroy 를 치지 않았다. 남은 경로는 자동 종료 장치가
  치는 `tofu destroy` → 정리 스크립트 하나뿐이다. 그래서 스크립트의 EC2 경로가 미검증이라는 것(Q5)이 가볍지 않다.

### 메타 교훈

**다섯 문제 전부 "누가 그 일을 하는가"를 잘못 짚으면 틀리는 문제였다.**

| 겉보기 | 실제 주체 |
|---|---|
| 노드가 바쁘니 Karpenter 가 늘린다 | 사용률을 보는 것은 HPA. Karpenter 는 Pending 파드만 본다 |
| 거절당하면 Karpenter 가 다른 종류로 간다 | 멈춘 주문서를 치울 주체가 없었다. 사람이 지웠다 |
| 노드를 줄이면 절약이다 | 줄인 것은 Karpenter, 그 대가(콜드 JVM)를 받아 다시 늘린 것은 HPA |
| destroy 가 다 지운다 | tofu 는 자기 장부만. Karpenter 의 것은 스크립트가 지워야 한다 |
| EC2 가 0대니 스크립트가 지웠다 | 지운 것은 Karpenter 였다 |

결과만 보면 다섯 번 다 "됐다"로 읽힌다. 주체를 물어야 빈 곳이 보인다.
