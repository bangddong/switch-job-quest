## Q1. `hpa 56%/70%`, 새 파드 4m · 기존 파드 220m. HPA 의 판단에서 무엇이 잘못됐나

- 사용자 답: *"HPA 가 모야"*
- 정오: ❌ (용어부터 설명 필요) → 교육 후 재확인

**해설**

① **무슨 작업 중이었나** — 초당 600건의 부하를 걸어 둔 채 15초마다 HPA 상태와 파드별 CPU 를 찍고 있었다.
HPA 가 `daily-api` 를 1개에서 2개로 늘린 직후다.

② **무엇이 관측됐나**
```
01:57:21  hpa 56%/70%  rep=2   새 파드 4m · 기존 파드 220m   (requests 는 둘 다 200m)
```

③ **왜 그런가** — HPA(Horizontal Pod Autoscaler)는 파드 개수를 자동으로 고치는 장치다. 15초마다
metrics-server 에 *"이 파드들이 CPU 를 얼마나 쓰나"* 를 묻고, 아래 식으로 필요한 개수를 구해
Deployment 의 `replicas` 를 바꾼다.
```
사용률       = 실제 사용량 ÷ requests(예약한 양)
필요 파드 수 = 올림( 현재 파드 수 × 현재 사용률 ÷ 목표 사용률 )
```
파드가 여러 개면 HPA 는 **평균 하나만** 본다. 새 파드 4÷200 = 2%, 기존 파드 220÷200 = 110%,
평균 56%. 목표 70% 아래라 *"충분하다"* 고 판단했다.

④ **안 그랬으면 어땠나** — `56%/70%` 만 보면 *"확장이 성공했고 여유가 생겼다"* 로 읽는다. 실제로는
기존 파드가 여전히 예약량을 넘겨 쓰고 있었다. 파드를 늘린 목적(기존 파드의 짐을 더는 것)이
달성되지 않았는데 지표는 달성됐다고 말한다.

⑤ **근거** — 일지 2026-10-08 `[막힘] P5` · `k8s/hpa/daily-api-hpa.yaml` (`averageUtilization: 70`) ·
`k8s/base/daily-api.yaml` (`requests.cpu: 200m`)

## Q1-재확인. 파드 3개(전부 200m 예약)가 300m · 10m · 20m 를 쓴다. 평균은, 그리고 HPA 는 늘리나

- 1차 사용자 답(같은 장면의 숫자를 다시 물었을 때): *"5%?"* → ❌. 사용률 = 쓴 양 ÷ 예약한 양임을 다시 설명
- 사용자 답: *"(150% + 5% + 10%) / 3 = 55. 안 늘리겠지"*
- 정오: ✅
- 근거: 위와 같은 식. 한 파드가 150% 인데도 평균 55% 라 아무 조치가 없다는 것까지 맞다

## Q2. 새 파드는 Ready 였는데 왜 80초 동안 요청을 거의 못 받았나

- 사용자 답: *"앞단 ALB 가 새 pod 를 인식하지 못하고 요청 전달을 안 했나?"*
- 정오: △ 부분
  - **맞은 것**: 원인을 파드가 아니라 요청을 나눠 주는 앞단에서 찾았다
  - **다른 것**: ①이 세션에는 ALB 가 없었다(계획서 D8). 앞단은 Service(ClusterIP)였다
    ②새 파드는 인식됐다 — `1/1 Ready` 가 되면 Service 의 엔드포인트 목록에 올라간다

**해설**

① **무슨 작업 중이었나** — Q1 과 같은 구간. k6 는 클러스터 안에서 `daily-api` 라는 Service 이름으로
요청을 보내고 있었다.

② **무엇이 관측됐나**
```
연결 재사용 켬   새 파드   4m · 기존 파드 220m          (01:57:21)
연결 재사용 끔   새 파드 483m · 새 파드 434m · 기존 파드 95m   (02:07:25, --no-connection-reuse)
```

③ **왜 그런가** — Service 는 파드를 **요청마다 고르지 않고 연결을 맺을 때 한 번만** 고른다. 요청을
보내려면 먼저 상대와 연결(TCP 통로)을 맺어야 하고, 매번 새로 맺으면 느려서 대부분의 클라이언트는
한 번 맺은 연결을 계속 쓴다(keep-alive). k6 도 그렇다. 파드가 1개일 때 맺은 연결은 전부 기존 파드에
붙어 있고, 파드가 2개가 된 뒤에도 그 연결로 요청이 간다. Service 가 새 파드를 고를 기회는
**새 연결이 생길 때뿐**이다.

④ **안 그랬으면 어땠나** — *"HPA 가 느리다"* 또는 *"새 파드에 문제가 있다"* 로 오진하고 HPA 설정이나
readiness 를 만지게 된다. 원인은 그 둘 어디에도 없다.

⑤ **근거** — 일지 2026-10-08 `[막힘] P5`. ⚠️ **미확인**: 재사용을 켠 회차에서 3분 뒤 균형이 맞은 것이
k6 가 기존 연결을 끊어서인지 추가 연결을 열어서인지는 로그를 남기지 않아 모른다. 확인된 것은
대조 결과(재사용을 끄면 즉시 분산)뿐이다.

## Q2-재확인. 설정을 안 바꿨는데 3분 뒤 두 파드가 110m · 125m 로 비슷해진 이유

- 사용자 답: *"기존 연결이 끊기고 새 연결이 발생됐기 때문에?"*
- 정오: ✅ (원리 정답. 연결이 실제로 왜 새로 생겼는지는 위 ⑤대로 미확인)

## Q3. 같은 요청량인데 새 파드가 처음에 CPU 를 5배(578m → 110m) 쓴 이유, 그리고 HPA 가 4개까지 늘린 것과의 관계

- 사용자 답: *"initialize 할 때 잠깐 치솟나?"*
- 정오: △ 부분
  - **맞은 것**: 갓 뜬 JVM 이 CPU 를 훨씬 많이 쓰는 시기가 있다
  - **다른 것**: 578m 는 초기화 때의 값이 아니다. 그 파드는 초기화가 끝나고 80초를 쉬고 있었다

**해설**

① **무슨 작업 중이었나** — 같은 부하(초당 600건)를 유지한 채 관찰 중. 새 파드가 막 요청을 받기 시작했다.

② **무엇이 관측됐나**
```
01:56:49  1575m   뜨는 중                 ← 초기화
01:57:21     4m   Ready, 요청 없음
01:58:24     2m   여전히 요청 없음
01:58:40   578m   요청이 들어오기 시작      ← 문제의 숫자.  hpa 198%/70% → New size: 4
02:01:19   110m   같은 요청량.             hpa 58%, 파드 2개
```

③ **왜 그런가** — 치솟은 것이 두 번이고 원인이 다르다. 첫 번째는 Spring 이 뜨며 클래스를 읽고 빈을
조립하는 초기화 비용이다. 두 번째가 **JIT 컴파일**이다. JVM 은 코드를 처음 만나면 바이트코드를 한 줄씩
해석해 실행한다(느리다). 자주 불리는 메서드는 먼저 가벼운 컴파일러(C1)가 빠르게 번역하고, 더 많이
불리면 무거운 컴파일러(C2)가 실행 통계를 보고 깊게 다시 번역한다. 번역이 끝나기 전에는 요청 처리가
느린 데다 번역 작업 자체(별도의 컴파일러 스레드)도 CPU 를 쓴다. **이 비용은 시간이 지나서가 아니라
코드를 실제로 실행해 봐야 치러진다** — 80초를 쉬었어도 요청이 안 왔으니 번역은 시작도 안 됐다.

HPA 는 그 578m 를 부하 증가로 읽었다: (578+215)÷2 = 396m → 198% → 2×198÷70 = 5.66 → 6개, 상한에
걸려 4개. 그렇게 추가로 뜬 3번째 파드가 다시 초기화로 1761m 를 찍어 평균을 더 올렸다.
**늘린 파드의 준비 비용이 또 늘릴 근거가 됐다.**

④ **안 그랬으면 어땠나** — *"초당 600건에는 파드 4개가 필요하다"* 로 결론 내고 용량을 두 배로 잡는다.
정상 상태에서 필요한 수는 2개였다. 또는 4번째가 Pending 인 것을 보고 노드를 늘린다.

⑤ **근거** — 일지 2026-10-08 `[막힘] 계획에 없던 발견`. JIT 의 단계 구조(C1/C2)는 HotSpot 의 일반 동작이며
이 세션에서 직접 관측한 것은 CPU 수치의 추이뿐이다. `be/Dockerfile` 의 `-XX:ReservedCodeCacheSize=96m`
가 번역 결과를 담는 공간의 상한이다. 09-08 실측에서 p95 가 부하와 함께 내려간 것(22.95 → 8.16ms)도 같은 현상.

- 사용자 답: *"아니지. 어차피 첫 요청은 JIT 컴파일러에 의해 컴파일된 게 없으니 비용은 발생해."*

## Q4. HPA 가 파드가 더 필요하다고 정확히 판단했는데 4번째가 왜 못 떴나. HPA 가 할 수 있는 일과 없는 일

- 사용자 답: *"모르겠어"*
- 정오: ❌ → 교육 후 재확인

**해설**

① **무슨 작업 중이었나** — Q3 의 과확장으로 HPA 가 `replicas` 를 4로 적은 직후.

② **무엇이 관측됐나**
```
FailedScheduling  daily-api-5657568fc6-jwq8p
0/4 nodes are available: 1 node(s) were unschedulable, 3 Insufficient memory.
```

③ **왜 그런가** — 노드는 실제 서버 한 대, 파드는 그 위에서 도는 앱 하나다. 파드를 어느 노드에 올릴지는
**스케줄러**가 정하는데, 파드가 예약하려는 만큼(`daily-api` 는 512Mi)의 빈자리가 있는 노드에만 올린다.
없으면 파드는 `Pending` 으로 남는다. 4대 중 1대는 k6 전용으로 막아 둔(cordon) 노드였고, 나머지 3대에는
512Mi 가 남아 있지 않았다. HPA 는 **`replicas` 숫자를 적어 넣을 뿐**이다. 파드를 노드에 올리는 것은
스케줄러의 일이고, 노드를 더 빌리는 것은 둘 다 못 한다. 그 일을 하는 것이 Karpenter(Stage 5b)다.

④ **안 그랬으면 어땠나** — HPA 설정을 고치려 든다(재확인 문제가 그 경우다).

⑤ **근거** — 일지 2026-10-08 `[해결] E2` · 계획서 §3 용량 산술(3개까지는 최악 배치에서도 들어간다고 예측했고 맞았다)

## Q5. 같은 배포 파일을 다시 적용했을 뿐인데 부하 중인 파드가 왜 죽었나. HPA 를 상시 쓰면 파일을 어떻게 해야 하나

- 사용자 답: *"레플리카를 2로 해야 하나? 그럼 롤링이 가능할 것 같은데"*
- 정오: ❌ → 교육 후 재확인
  - 숫자를 2로 바꿔도 HPA 가 4로 늘린 것을 2로 되돌린다. 롤링 배포는 버전 교체의 문제라 다른 축이다
    (참고: `daily-api` 는 `strategy: Recreate`)

**해설**

① **무슨 작업 중이었나** — 부하 중, HPA 가 4개를 원하는 상태에서 `k8s/base/daily-api.yaml` 을 일부러
다시 적용해 봤다(계획서 E1).

② **무엇이 관측됐나**
```
02:07:41  kubectl apply          (매니페스트 replicas: 1)
02:07:47  파드 1개만 남음
02:08:17  HPA 가 2로 다시 늘림
```

③ **왜 그런가** — 파드 개수는 Deployment 의 `replicas` 칸 하나에 적혀 있고, 그 칸에 쓰는 주체가 둘이었다.
HPA 는 15초마다 계산값을, `kubectl apply` 는 파일에 적힌 값을 쓴다. apply 는 *"클러스터를 이 파일대로
맞춰라"* 이므로 `replicas: 1` 이 적혀 있으면 그 칸을 1로 되돌리고 남는 파드를 정리한다. HPA 를 상시 쓰는
서비스는 매니페스트에서 **`replicas` 줄을 뺀다** — 파일에 없는 칸은 apply 가 건드리지 않는다.

④ **안 그랬으면 어땠나** — 배포할 때마다 처리 능력이 떨어지는 구간이 생기는데 원인을 배포 자체
(이미지·설정 변경)에서 찾게 된다.

⑤ **근거** — 일지 2026-10-08 `[해결] E1` · `k8s/base/daily-api.yaml` (`replicas: 1`). ⚠️ **미확인**: 이미 줄이
있던 매니페스트에서 처음 지우고 적용할 때 값이 기본값 1로 한 번 돌아갈 수 있다는 것은 일반 지식이고
이 세션에서 실측하지 않았다.
