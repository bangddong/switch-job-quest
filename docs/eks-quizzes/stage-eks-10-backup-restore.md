## Q1. `Retain` vs `Delete` — 3a 였다면 리허설이 성립했을까?

`kubectl delete pvc/pv` 가 1초 만에 끝났고 EBS 는 `available` 로 살아남았다.
Stage 3a(동적 PVC, `reclaimPolicy: Delete`)였다면 같은 두 명령이 어떻게 달랐을까?
그리고 3a 에서라면 볼륨을 따로 파괴하는 단계 없이 리허설이 성립했을까?

- **사용자 답**: 모르겠어
- **정오**: ❌ (첫 접촉)
- **해설**:
  - 3a 는 StorageClass 가 `reclaimPolicy: Delete` 라 PVC 를 지우면 PV 가 `Released` 가 되면서
    **CSI 가 EBS 까지 삭제한다**. 즉 3a 에서는 `kubectl delete pvc` 가 곧 볼륨 파괴다.
  - 3b 는 사슬을 **두 군데서** 끊는다: PV 의 `persistentVolumeReclaimPolicy: Retain`,
    그리고 IAM — CSI 삭제 조건 태그 3종이 없어 `ec2:DeleteVolume` 조건이 불충족이다.
    그래서 `aws ec2 delete-volume` 을 **내 크리덴셜로** 따로 쳐야 했다.
    *"컨트롤러는 못 지우고 사람은 의도적으로 지울 수 있다"* — 설계대로.
  - 🔑 **두 번째 질문의 답이 더 중요하다: 기계적으로는 쉬워지고 의미상으로는 정반대다.**
    3a 볼륨은 세션과 함께 사라지는 것이 **설계**다. 잃을 것이 없으면 백업할 것도 없다 —
    리허설이 성립하는 게 아니라 **리허설할 대상이 없다.** 리허설이 의미를 갖는 이유는
    3b 가 *"부숴도 남는다"* 고 **약속하기 때문**이고, 약속이 위험을 만든다.
  - 🔑 **파괴는 필요조건이지 충분조건이 아니다.** 3a 에서 볼륨이 사라져도 복구 후 26행으로
    판정하면 여전히 Flyway 재시드와 구별되지 않는다. **센티넬은 파괴 방식과 독립적으로 필요하다.**
- **근거**: `k8s/base/postgres.yaml` `reclaimPolicy: Delete` · `postgres-static.yaml:78`
  `Retain` · `infra/aws-eks/0-bootstrap/ebs-postgres.tf:75-96` IAM 자물쇠 ·
  일지 `③ 파괴` (delete pvc/pv 1초, EBS available)

## Q2. `CASE` 가 왜 없는 테이블을 막아주지 못했나?

```sql
SELECT CASE WHEN to_regclass('public.backup_sentinel') IS NULL THEN 0
            ELSE (SELECT count(*) FROM backup_sentinel WHERE token='...') END;
→ ERROR: relation "backup_sentinel" does not exist
```

- **사용자 답**: 쿼리 실행 전 해석하기 때문에?
- **정오**: ✅
- **해설 보강**: PostgreSQL 은 **parse → analyze → plan → execute**. `FROM backup_sentinel` 은
  **이름**이고 이름 해석은 analyze 에서 끝난다. `CASE` 는 **executor 가 다루는 것**이라 거기까지
  가지도 못한다. `to_regclass()` 가 NULL 을 주는 건 **런타임 값**, `FROM backup_sentinel` 은
  **파스타임 이름** — 같은 문장 안에 있어도 **다른 단계**에서 처리되므로 앞이 뒤를 보호할 수 없다
  (플래너는 실행 결과를 모르는 채 컬럼 타입·개수를 먼저 알아야 한다).
  → `to_regclass` 는 **테이블 이름을 정적으로 참조하지 않는 문장**에서만 쓸모가 있다.
  한 문장으로 하려면 `PL/pgSQL`의 `EXECUTE`(동적 SQL)로 파싱 시점을 런타임까지 밀어야 한다.
- **두 번째 층**: 그 psql 이 ERROR 를 뱉고도 `rc=0` 을 냈다(`ON_ERROR_STOP` off).
  스크립트가 빈 문자열을 받아 **"센티넬이 아직 있다"** 고 보고했다 — 멈춘 방향은 안전했지만
  원인 표시가 틀렸다. 🔑 **이 스크립트의 복구 경로에 대해 내가 주석으로 경고해둔 함정을
  바로 옆 판정 함수에서 밟았다.**
- **근거**: 일지 `④ 재생성 + 복구` 막힘/해결 · `db-restore.sh` `sentinel_count()`

## Q3. #416 보다 길었는데 왜 쌌나? 여기서 나오는 운영 규칙은?

```
#416  30m44s $0.0996   |   이번  32m10s $0.0848
```

- **사용자 답**: 모르겠어!
- **정오**: ❌ (첫 접촉)
- **해설**: 시간이 아니라 **시간당 단가**가 바뀌었다.
  `#416 = $0.100 + $0.0283×3 = $0.1849/h` vs `이번 = $0.100 + $0.0283×2 = $0.1566/h`.
  | | #416 | 이번 | 차 |
  |---|---|---|---|
  | 컨트롤플레인 | $0.0512 | $0.0536 | +$0.0024 (더 길어서) |
  | 노드 | $0.0435 (3대) | $0.0303 (2대) | **−$0.0132** |
  | ALB | $0.0040 | — | −$0.0040 |
⚠️ 위 `−$0.0132` 는 **두 세션 line item 의 차**다 — 정확하지만 **기간 차가 섞여 있다.**
*"노드 한 대 줄여 아낀 돈"* 이라는 질문의 답은 **같은 기간 노드 1대 값**이다:
```
0.5361 h × $0.0283 = $0.0152     ← 이쪽이 그 질문의 답
시간 증가분          = $0.0024
비율                = 6.3배  (초판에 "5배"라고 적었다)
```
🔑 **초판은 line item 차에 그 라벨을 붙였다** — QA F-11 이 잡았다.
***#414 메타 교훈이 이 문서 안에서 그대로 재발한 것이다: 숫자는 맞는데
그 숫자가 답하는 질문이 내가 던진 질문이 아니었다.***
그리고 이 오류는 **정정 커밋에서 "전수로 찾았다"고 적은 직후에도 여기 남아 있었다** —
CONTEXT 와 PR 본문만 고치고 퀴즈 문서를 빠뜨렸다. 전수의 범위를 내가 정하고 있었다.
- 🔑 **규칙 — 레버가 둘인데 당길 수 있는 시점이 다르다.**
  | 레버 | 언제만 | |
  |---|---|---|
  | **단가**(노드 수·ALB) | **apply 전에만** | → *"필요한 최소로 띄운다"*. 승인 게이트 시점에 확정 |
  | **시간** | **세션 중에만** | → *"$0 구간에서 할 수 있는 건 전부 $0 구간에서"* |
- 🔑 **하한이 있다**: 컨트롤플레인 $0.100/h 는 끌 수 없고 이번 세션의 **63%**.
  → **세션을 쪼개면 손해다**(컨트롤플레인을 두 번 낸다). 09-06 의 *"묻느라 기다리느니
  destroy 후 재apply"* 손익분기 19분 ≈ $0.059 가 바로 이 산술이다.

## Q4. daily-api 를 안 내리면 왜 **core-api** 가 못 뜨나?

- **사용자 답**: flyway 마이그레이션 파일이 나누어져있기 때문?
- **정오**: ✅ (메커니즘 정확)
- **해설 보강**: 분포 실측 — core-api `V1~V6·V8·V9`(8개) / db-core `V7·V10~V13`(5개) = **13개**
  (`Successfully validated 13 migrations` 과 일치). `db-core` 의 `FlywayConfig` 가 `migrate()`
  앞에 `repair()` 를 도는데, `repair()` 는 **"지금 클래스패스의 파일 집합"** 과 DB 이력을 맞춘다.
  daily-api 클래스패스에 core-api 파일이 없으므로 그 버전들을 `DELETED` 로 마킹 → core-api 검증 실패.
- 🔴 **이 문항이 내 코드 주석의 과장을 잡았다 (#416 Q2-2 와 같은 형태의 수확).**
  `daily-api/application-prod.yml:30` — *"의도적으로 `migrate-on-startup` 을 켜지 않는다"*,
  `FlywayConfig.kt` `@ConditionalOnProperty(matchIfMissing = false)`.
  **repair() 위험은 설정 게이트로 이미 막혀 있다**(07-01 V8 사고 뒤 구조로 고친 결과).
  그런데 `db-restore.sh` 헤더 ③은 조건절 없이 단정했다. Blindspot 보고서는
  *"migrate-on-startup 을 켜면"* 이라고 조건을 달았는데 **내가 옮기면서 떨어뜨렸다.**

  | 층 | 지금 살아 있나 | 무엇이 막고 있나 |
  |---|---|---|
  | **커넥션 간섭** — daily-api 가 DB 커넥션을 문 채 `pg_restore --clean` 이 DROP/재생성 | ✅ **현재 위험** | 아무것도 — **이 스크립트뿐** |
  | `repair()` 의 DELETED 마킹 | ⚪ **잠재** | `matchIfMissing = false` + 설정 미기재 |

  🔑 **잠재를 현재처럼 적으면 둘 다 나빠진다**: 독자가 게이트의 존재를 몰라 무심코 열 수 있고,
  반대로 *"이미 막혀 있네"* 를 알아챈 순간 **지금 진짜 필요한 이유(커넥션)까지 같이 무시한다.**
  → `db-restore.sh` ③ 과 테스트 ⑤의 "무엇의 실패를 잡나" 를 두 층으로 분리해 정정했다.
- **근거**: `be/core/core-api/src/main/resources/db/migration/` · `be/storage/db-core/.../db/migration/` ·
  `FlywayConfig.kt:40-46` · `daily-api/application-prod.yml:30-32`
