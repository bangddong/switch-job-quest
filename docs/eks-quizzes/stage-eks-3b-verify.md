## Q1 — 데이터는 살았는데 왜 로그인이 실패했나

- 답변: *"다시 지을 때 destroy 이전의 패스워드를 들고 있어서? init 할 때 나오는 걸 그대로 들고있었던거지"*
- 정오: ❌ **부분정답 — 절반이 정확, 그리고 더 어려운 쪽을 맞혔다**
- 맞은 것: postgres 이미지는 `POSTGRES_PASSWORD`를 **`initdb` 시점에만** 쓴다. 데이터 디렉토리가
  있으면 읽지도 않는다. 실측 로그 `PostgreSQL Database directory appears to contain a database;
  Skipping initialization` 이 그 증거.
- 빠진 것: **반대편이 왜 달라졌는가.** 양쪽이 어긋나려면 한쪽이 바뀌어야 하고, 바뀐 건 앱 쪽이다.
  ```
  infra/aws-eks/2-cluster/secrets.tf:100   resource "random_password" "postgres" { ... }
  infra/aws-eks/2-cluster/secrets.tf:92      password = random_password.postgres[0].result
  ```
  `random_password`는 생성값을 **tfstate에 저장**해 재사용한다. `tofu destroy`가 state에서 리소스를
  지우므로 재apply에서 **새로 생성**되고, 그 값이 Secrets Manager → ESO → K8s Secret → 앱으로 흘렀다.
  ```
  볼륨 (0-bootstrap 소유, destroy 무관) ──► 옛 비밀번호 해시   ← 안 바뀜
  tfstate (2-cluster 소유, destroy됨)   ──► 새 비밀번호       ← 바뀜
  ```
  **두 저장소의 수명이 다른데 같은 비밀을 담고 있었다.** → 원장 `L-14`

### Q1-b (객관식 재확인) — `ignore_changes`로 고칠 수 있나

- 답변: **다** (해결되지만 destroy가 실패하게 된다)
- 정오: ❌ (정답: **나** — state에서 사라진 뒤엔 무시할 diff 자체가 없다)
- 오답 근거 평가: **3b에서 밟은 `prevent_destroy` 사건을 떠올려 `lifecycle` 블록 = destroy 망가짐으로
  일반화했다.** 관련 있는 기억을 잘못 적용한 것이라, 무지가 아니라 과잉일반화.
  `prevent_destroy`는 **파괴 정책**, `ignore_changes`는 **비교 정책**이다.
- 🔬 **$0 실증** (`random` provider만 사용, AWS 비용 0):
  ```
  ① 최초 apply            → DMsI65…
  ② 재apply (state 유지)  → DMsI65…    ← ignore_changes 작동
  ③ destroy               → Destroy complete!   ← 실패하지 않는다 ('다' 반증)
  ④ destroy 후 재apply    → wlo88E…    ← 🔴 바뀌었다 ('나' 확정)
  ```
  ⚠️ **이 실증의 1차 시도가 거짓 통과했다.** HCL 문법 오류로 apply가 전부 실패해 비교 대상이
  **빈 문자열 두 개**였는데, `[ "$A" = "$C" ]`가 참이라 *"'가'가 정답"* 을 출력했다.
  빈 값 가드를 넣고 재실행해서 잡았다. **검사기를 만들다 검사기의 병에 걸린 사례로 남긴다.**

## Q2 — 왜 `initdb` 건너뜀이 행 개수보다 강한 증거인가

- 답변: *"저 문구 자체가 directory에 있어서 initialized를 안한다는거자나"*
- 정오: ❌ **부분정답** — 로그 해석은 정확하나 "행 개수로 못 배제하는 것"에는 미도달
- 교정: `tech_question_bank` 26행은 **마이그레이션이 만드는 숫자**다(V10 5행 + V11 21행).
  빈 볼륨에 `initdb`가 돌고 Flyway가 13개를 새로 적용해도 **똑같이 26이 나온다.**
  → 26행은 *"살아남았다"* 와 *"똑같이 다시 만들어졌다"* 를 **구분하지 못한다.**
  (리포트에 26행을 인용한 것 자체가 가장 약한 증거를 든 것이었다.)
  `initdb` 건너뜀은 **층이 다르다** — DB 내용이 아니라 **스토리지**에 대한 진술.
  여기에 `database system was shut down at 2026-08-07 15:17:08 KST`(이전 클러스터의 종료 시각)가
  더해지면 재생성 가설이 배제된다.
  > **행 개수 = 동등성(내용이 같다) · `initdb` 건너뜀 = 동일성(같은 것이다).**
  > Stage 3b가 묻는 것은 동일성이다.

## Q5 — 왜 머지 ref 우회 대신 재빌드를 골랐나

- 답변: (무응답)
- 교정: **검사의 목적이 초록불이 아니라 추적성**이기 때문.

  | | 우회(머지 ref fetch) | 채택안(main에서 재빌드) |
  |---|---|---|
  | 검사 통과 | ✅ | ✅ |
  | 태그로 코드를 찾을 수 있나 | ❌ 여전히 히스토리에 없다 | ✅ 태그 = main 커밋 |
  | 6개월 뒤에도 되나 | ❌ GitHub이 머지 ref를 정리할 수 있다 | ✅ |

  우회는 **지표를 만족시키고 성질은 안 만족시킨다.** 재빌드는 부작용이 아니라 본체 —
  태그가 main 커밋이 되는 순간 *"배포된 이미지 = main의 상태"* 가 **구조로** 보장된다.
  실측: `SHA = f8f1a190…` = `git rev-parse main`.

### Q5-b (객관식 재확인) — 같은 정신의 처방은

- 답변: **가** (probe를 `/health`로 되돌린다)
- 정오: ❌ (정답: **다** — readiness 그룹을 `db,ping`으로 **정의**한다)
- 🔴 **이 오답이 이번 퀴즈에서 가장 값지다 — `가`는 우리가 지금 실제로 하고 있는 것이고,
  그게 오늘 하루 종일 이름 붙인 그 병이다.**
  ```kotlin
  // be/core/core-api/.../HealthController.kt:10
  @GetMapping("/health")
  fun health(): ApiResponse<String> = ApiResponse.success("DevQuest API is running")
  ```
  ```yaml
  # k8s/base/core-api.yaml:105
  readinessProbe:
    httpGet: { path: /health, port: http }
  ```
  **readiness가 "요청을 처리할 수 있나"를 주장하면서 "서블릿 스레드가 상수를 반환할 수 있나"만
  검사한다.** DB가 죽어도 200 → Ready → 트래픽 유입 → 전부 500.
  `/actuator/health`는 반대로 **너무 빡빡**(메일까지 AND)하고 `/health`는 **너무 헐겁다**.
  `다`가 정답인 이유는 그것만이 **"readiness가 무엇을 뜻하는지 먼저 정의"** 하기 때문.
  `나`(mail 끄기)는 지표 조정일 뿐, `라`(threshold 늘리기)는 **고장난 신호 무시**라 최악.

### 최종 재확인 — 그럼 `/health` 컨트롤러는

- 답변: **가** (그대로 둔다 — liveness가 쓰고, liveness는 DB를 보면 안 된다)
- 정오: ✅ **정답**

  | | 묻는 것 | 의존성을 봐야 하나 |
  |---|---|---|
  | liveness | *"이 프로세스를 재시작해야 하나"* | ❌ **절대 안 된다** |
  | readiness | *"지금 트래픽을 받아도 되나"* | ✅ 봐야 한다 |

  liveness가 DB를 보면 DB가 흔들릴 때 **모든 파드가 동시에 재시작**하고, 재시작 폭풍이 DB를
  더 밀어붙인다 — **장애를 복구하는 게 아니라 증폭시킨다.**
  `/health`(상수 반환)는 **liveness용으로는 정확히 옳은 설계**다. 문제는 readiness에도 쓰인다는 것뿐.

## 메타 교훈

> **다섯 문제가 전부 "검사가 주장보다 헐겁거나 빡빡했다"였다.**

> - 비밀번호는 *"영속"* 을 주장하는데 **세션 state**에 살았다

>
