## Q1. `limits: 900Mi` 를 낮춰도 왜 메모리가 거의 안 주나

- 사용자 답(1차, 서술형): *"잘 모르겠어"*
- 정오: ❌ → 교육 후 재확인
- 근거: `/actuator/prometheus` 실측 — heap commit **139.3Mi**(used 70.3) vs
  nonheap commit **183.4Mi**(Metaspace **125.6** + CodeCache 40.6 + CCS 17.2), 네이티브 ~53Mi.
  **힙은 상한 316Mi 중 70Mi 만 썼다** — 천장에 닿은 적이 없다.
  `MaxRAMPercentage=35.0` 은 **힙에만** 비례하고 `MaxMetaspaceSize=160m`·`ReservedCodeCacheSize=96m` 은
  **고정**이다(`be/Dockerfile:62-68`) → `limits` 를 조이면 **조여지는 건 힙뿐**.

### Q1-2 (재확인, 객관식) `limits` 900→512Mi 로 낮추면 실사용은?
- 사용자 답: **B** (거의 그대로 ~350~376Mi)
- 정오: ✅
- 근거: 힙 커밋만 소폭 감소, nonheap 183.4Mi + 네이티브 53Mi 는 불변.
  오답 C(OOMKill)는 `376 < 512` 로 배제 — 단 여유 136Mi 가 더 낮출 때의 진짜 제약이다.

## Q2. 59,889 요청 전부 200, 에러 0건. 왜 좋은 소식이 아닌가

- 사용자 답(1차, 서술형): *"부하 테스트에 대한 신뢰도가 떨어지기 때문?"*
- 정오: 🟡 **부분정답** — 결론은 맞으나 그것이 증명 대상이라 순환. 방향은 정확했다.
- 근거: ①에러 0 = **한계 미도달** → 401Mi 는 최대가 아니라 **하한** ②**closed loop 에선 에러 0 이
  거의 보장된다** — 워커가 응답을 기다리므로 서버가 느려지면 부하가 **자동으로 줄어든다**.
  즉 "에러 0"은 서버에 대해 거의 아무 정보가 없는 **반증 불가 관측**이다
  ③회전당 180ms 중 상당량이 `wget` fork/exec → **클라이언트가 병목이었을 가능성**.

### Q2-2 (재확인, 객관식) 서버가 10,341 req/s 를 성공 처리했는데 k6 가 실패 판정한 이유
- 사용자 답: **B** (생성기가 목표를 못 만들었고 `dropped_iterations` 로 보고)
- 정오: ✅
- 근거: 로컬 실측 `RATE=20000` → `http_reqs 56628 (10341/s)` · `dropped_iterations 81126` · exit **99**.
  **이것이 09-06 셸 루프에 없던 통제다** — 서버 무죄 / 생성기 유죄를 구분한다.

## Q3. `ws = memory.current − inactive_file` 로 계산한 이유, postgres 만 차이나는 이유

- 사용자 답(1차, 서술형): *"모르겠다!"*
- 정오: ❌ → 교육 후 재확인
- 근거: `memory.current = anon + file + slab`. **anon** 은 회수 불가(못 주면 OOMKill),
  **file**(페이지 캐시)은 압박 시 그냥 버린다. JVM 은 jar 를 한 번 읽고 익명 메모리에서 놀아
  `file` 0~1Mi 인데, **postgres 는 버퍼드 I/O** 라 `file` 25Mi.
  실측 대비: postgres idle→부하에서 **`anon` 11→32Mi(실제 작업), `file` 25→24Mi(불변)**.
  `current` 로 requests 를 잡으면 **버려질 캐시에 노드 용량을 묶는다.**
  📌 이건 k8s 의 `working_set = usage − total_inactive_file` 정의와 동일.

### Q3-2 (재확인, 객관식) `current 420 / anon 60 / inactive_file 340` 일 때 requests
- 사용자 답: **B** (80Mi 기준)
- 정오: ✅

## Q4. `ai-api` W_peak 212Mi 인데 왜 limits 를 320Mi 가 아니라 448Mi 로 잡나

- 사용자 답(1차, 서술형): *"??"*
- 정오: ❌ → 교육 후 재확인
- 근거: limits 320Mi → MaxHeap 112Mi. **112 + 160(Metaspace 고정) + 96(CodeCache 고정) = 368 > 320**.
  JVM 이 "써도 된다"고 아는 양이 컨테이너 허용치를 **48Mi 초과**한다 = 구성 모순.
  실패 방식이 고약하다 — JVM 이 막기 전에 컨테이너가 먼저 막으면 `OutOfMemoryError` 가 아니라
  커널 **SIGKILL**(`Exit Code 137`)이라 **스택트레이스도 GC 로그도 안 남는다**.
  (07-14 prod Metaspace 사고는 GC 로그가 결정적 증거였다 — `Dockerfile:41`)
  부등식 `0.35L + 160 + 96 ≤ L ⇒ L ≥ 393.8Mi` → 64Mi 단위로 **448Mi**(여유 36Mi).

### Q4-2 (재확인, 객관식) 하한 448Mi 를 postgres 에도 적용하나
- 사용자 답: **B** (아니다 — 근거가 JVM 플래그 부등식이라 성립 안 함)
- 정오: ✅
- 근거: 적용했으면 postgres limits 를 128 → 448Mi 로 **3.5배** 부풀렸다.
  🔑 **규칙의 적용 범위는 규칙의 근거에서 나온다.**

## Q5. 왜 "질문하지 마라"가 아니라 "먼저 destroy 하고 물어라"인가

- 사용자 답(1차, 서술형): *"질문이 있었을 때 사용자의 답변이 돌아오는 시간까지를 측정할 수 없기 때문?"*
- 정오: 🟡 **부분정답 — 그리고 더 중요한 절반을 짚었다.** 숫자가 빠졌을 뿐 메커니즘이 정확하다.
- 근거: 켜둠 $0.0031/분 vs 재apply+destroy 19분 **고정** $0.059 → **손익분기 19분**.
  비대칭이 핵심 — 지우는 쪽은 **고정**, 켜두는 쪽은 **대기에 비례**. 실제 127분 대기 = $0.395
  (지웠으면 $0.059, **$0.336 절약**). 📌 리퍼가 2h 에 끊어 최대 $0.373 으로 **묶이긴 한다** —
  안전망은 바닥을 깔 뿐 좋은 선택을 대신하지 않는다.

### Q5-2 (재확인, **서술형** — 형식 변경 후 첫 문제)
> 램프 스테이지 3 에서 `dropped_iterations=0` 인데 p95 가 8배로 뛰었다. 계획에 없는 상황이다.
> 클러스터가 켜져 있는 지금 무엇을 하겠나?

- 사용자 답: *"켠 김에 다양한 부하를 걸어보며 어디서 병목이 발생되는지 확인 후 끄고 조치할 것 같은데?"*
- 정오: ✅ **정답. 그리고 규칙을 과잉적용하지 않은 것이 좋다.**
- 근거: SOP 규칙은 *"사용자에게 **질문**하지 마라"* 지 *"계획 밖의 일을 하지 마라"* 가 아니다.
  **사람의 답 대기 = 무한 / 데이터 추가 수집 = 유한**(스테이지 1개 ≈ 1분 ≈ $0.003)이고,
  지금 안 재면 재현 비용 $0.059 + 재현 실패 위험이 붙는다.
- 보완(채점 시 덧붙임): **탐색에도 상한을 먼저 박는다.** 안 그러면 무한 대기의 주체가
  사용자에서 **에이전트**로 바뀔 뿐이다(08-31 이 과금 중 진단으로 51분). 다만 이번엔 계측을
  미리 붙여둬서 **열린 탐색이 아니라 3지선다**다 — `nr_throttled`(CPU 스로틀) / GC `Pause` 델타 /
  postgres `anon`·CPU. 셋 다 명령 한 줄.

## 메타 교훈 — **숫자는 맞는데, 그 숫자가 답하는 질문이 다르다**

| 숫자 | 읽기 쉬운 오독 | 실제로 답하는 것 |
|---|---|---|
| MaxHeap **316Mi** | 힙이 이만큼 쓴다 | **써도 된다** (실제 70Mi) |
| **200** × 59,889 | 서버가 여유롭다 | **처리는 했다** (한계는 미상) |
| current **420Mi** | 이만큼 필요하다 | **차지했다** (340은 버려도 됨) |
| 하한 **448Mi** | 모든 컨테이너의 최소 | **JVM 구성의** 최소 |
| 재생성 **9분** | 지우는 게 비싸다 | 고정비 19분 **vs 무한** |

전부 **"허용치 / 관측치 / 점유량"을 "필요량"으로 읽어서** 생기는 오류다.
🔴 그리고 **09-05·09-06 에 내가 실제로 그렇게 틀렸다** — `limits` 를 낮추면 될 거라 믿었고
(Q1), 에러 0 을 성공으로 읽었다(Q2). 퀴즈가 사용자만 시험한 게 아니다.
