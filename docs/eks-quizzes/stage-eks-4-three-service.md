## Q1. EKS 노드그룹의 `health.issues` 가 왜 비어 있었나 (층 분리)

- 사용자 답 ①: *"우리가 쓰려던 인스턴스가 프리티어에선 사용할 수 없는 사양이었다"*
  → ❌ **근본 원인은 맞으나 질문(층 구조)에는 미답.** 원인은 이미 제시된 정보였다.
- 사용자 답 ② (객관식): `C` → ❌ (정답 `B`). **오답 경위가 유의미하다** — C(노드 Ready인데 파드 Pending)는
  **오늘 실제로 2차 apply 에서 일어난 일**이라, 서로 다른 층의 두 실패를 혼동한 것.
- 사용자 답 ③: `B` → ✅
- **정오: ✅ (3차)**
- 근거: 관리형 노드그룹은 ASG 를 감싼 얇은 층이다. EC2 는 ASG 가 만들고, EKS 는 *"노드가 join 했는가"* 만 본다.
  ASG 가 backoff 로 **재시도**하는 동안(06:35→06:36→06:38→06:42→06:50, 간격 증가) 위층에서는
  "진행 중" 과 구별되지 않는다. 🔑 **재시도는 hard failure 를 "느림" 으로 위장한다.**
  판별 기준: **인스턴스가 존재하는가** — 없으면 `kubectl` 은 원리적으로 못 본다.
- ⚠️ **출제 결함**: Q1-c 의 보기 A(IAM 정책 누락)도 엄밀히는 `kubectl` 로 진단 불가였다
  (인증 자체가 실패하면 CSR 도 안 남는다). 정답이 둘이었다 — A 를 *"kubelet 이 등록은 시도하는"*
  상황으로 썼어야 했다. 사용자가 의도한 답을 골랐으므로 정답 처리.

## Q2. `cancelled` 가 `failure` 보다 위험한 이유

- 사용자 답: *"ai-api 파드는 부팅되지 못했겠지?"* → ✅
- **정오: ✅ (1차)**
- 근거: `ImagePullBackOff` (재시도 간격이 최대 5분까지 벌어져 기다릴수록 느려진다).
  핵심은 **발견 시점**이다 — `failure`(빨간 X)면 **과금 전** CI 에서 /bin/zsh 에 발견하고,
  `cancelled`(회색)면 **과금 중** 파드가 안 뜬 뒤에 발견한다.
  오늘은 SOP §2b 사전 점검의 `describe-images` → `None` 이 /bin/zsh 에 잡았다.

## Q3. 2048Mi 가 959Mi 가 되기까지 (세 번의 삭감)

- 사용자 답 ①: *"잘 모르겠어"* → 교육 전환
- 사용자 답 ② (Q3-b, max_pods 17 이면 allocatable 은?): `B`(늘어난다) → ❌ (정답 `C` 줄어든다)
- 사용자 답 ③ (Q3-c, medium 은 2배? 더? 덜?): `C`(덜) → ❌ (정답 `B` 더).
  **부분정답**: 방금 배운 *"파드 상한↑ → kube-reserved↑"* 를 정확히 적용했다. 놓친 것은 그 효과의 **크기**.
- 사용자 답 ④ (Q3-d, 순증 얼마?): *"1800Mi 정도"* → ✅ (1841 − 66 = **1775Mi**)
- **정오: ✅ (4차)**
- 근거 (실측):
  ```
  2048Mi 공칭 → ① 커널·하이퍼바이저 -207 → 1841Mi capacity
              → ② kube-reserved + eviction -476 → 1365Mi allocatable
              → ③ 시스템 파드 requests -406 → 959Mi 우리 몫
  ```
  ②의 공식이 정확히 맞아떨어진다: `255Mi + 11Mi × max_pods(11) = 376Mi` + `eviction 100Mi` = **476Mi**.
  🔑 **파드 상한이 메모리를 먹는다** — max_pods 가 공식에 들어 있어 파드 슬롯과 메모리는 독립이 아니다.
  🔑 **고정비 대 변동비**: 고정비 761Mi(255 + 100 + 406) 는 한 번만, 변동비는 파드당 11Mi.
  물리 +1841Mi 에 추가 예약은 +66Mi 뿐 → 작은 노드일수록 고정비 비율이 잔인하다(small 은 37%).

## Q4. arm64 → x86 전환의 대가

- 사용자 답: *"이미지 빌드?"* → ✅
- **정오: ✅ (2차 — 중간에 스케일 아웃 질문으로 우회)**
- 근거: `ecr-push.yml` `runs-on: ubuntu-24.04-arm` → x86 러너, `nodes.tf` `ami_type` →

## Q5. C-3 의 완료 기준은 무엇을 증명했나

- 사용자 답 ①: *"모르겠어"* → 교육 전환
- 사용자 답 ② (Q5-b, 같은 함정은?): `A` → ❌ (정답 `B`). A 는 오히려 좋은 기준(결과 상태를 질의).
- 사용자 답 ③ (Q5-c, `Apply complete!` 는 좋은 기준인가?):
  *"tofu 파일 apply만 됐고 실제 기동 상태는 보장되지 않을 것 같은데?"* → ✅
- **정오: ✅ (3차)**
- 근거: C-3 의 근거는 **수단**(레포 존재 + 워크플로 옵션)을 증명했고 **결과**(이미지 존재)를 증명하지 않았다.
  ```
  ❌ 레포 생성 확인 + ecr-push.yml options 에 추가
  ✅ aws ecr describe-images 가 서비스 3개 각각 태그를 반환 + 그 태그가 main 의 조상
  ```
  🔑 **이 레포는 이미 이 원리를 알고 있었다** — `networkpolicy-ai-api.yaml`:
  *"'created 됐다' 는 증명이 아니다. 차단/허용 쌍으로만 증명된다."*
  같은 원리를 한 곳에 적고 **일반화하지 않았다.**
  🔑 판별 도구: **"이 문장이 거짓이 되려면 무엇이 일어나야 하나?"** 답이 "거의 없다" 면 정보량 0 이다.
  (`Apply complete!` 도 같은 함정 — README 가 이미 *"그건 '보냈다' 만 말한다"* 고 경고했다.)

## 🔴 이 퀴즈에서 실제로 일어난 가장 중요한 일

**Q4 도중 사용자가 계획서의 오류를 찾았다.**

> *"여러대의 EC2를 활용하는 스케일 아웃은 불가능한 상황이야?"*

→ 가능할 뿐 아니라 **x86 전환보다 낫다.** D-009 가 *"노드 2대"* 를 기각한 사유 셋 중 둘이 썩어 있었다:

- *"비용 +$0.026/h 로 medium 보다 비싸다"* — medium 단가가 **추정**이던 시점의 문장. 나중에
  **실측으로 정확히 2배**임이 확인되며 `2×small = 1×medium` 로 **동일 비용**이 됐는데,
  아무도 기각 사유로 돌아가지 않았다.
- *"파드당 512Mi 메모리 벽은 그대로"* — **논점 이탈.** 스케일 아웃이 푸는 것은 **총량**이다.

👉 **교훈: 추정이 실측으로 바뀌면, 그 추정에 기대 기각했던 대안을 반드시 다시 연다.**
CLAUDE.md 의 빨간 깃발 *"이건 일지에 적어뒀으니 됐어"* 가 정확히 이 모양이었다 —
실측을 **기록**은 했지만 그 실측이 무효화하는 **결정에 반영**하지 않았다.

`node_max_size` 는 처음부터 **2** 였다(`variables.tf:102`). 출제자가 안 봤다.
→ D-010 재개 경로를 정정했다: **1순위 노드 2대**, 2순위 x86.
