## Q1. `--resolve` 로 DNS 없이 HTTPS 검증이 성립한 두 조건 / 무엇이 깨뜨리나 / `-k` 를 안 붙인 것이 왜 판정의 핵심인가

- 사용자 답: 모르겠음
- 정오: ❌ → 교육 후 재확인
- 근거: `k8s/base/ingress.yaml` `rules:` 에 `host:` **0건** · `describe-listener-certificates` (인증서는 리스너 속성)

**해설 요지**
- 조건① Ingress 에 `host:` 가 없어 ALB 규칙에 Host 조건이 안 붙는다 → 어떤 Host 헤더로도 라우팅
- 조건② 인증서가 리스너에 고정 부착 · 1장뿐이라 SNI 무관하게 같은 cert
- `--resolve` 는 **DNS 만** 건너뛴다. `-k` 는 **검증을 끈다** — 전자는 판정을 유지하고 후자는 파괴한다
  ```
  *  subject: CN=eks.quest.dhbang.co.kr
  *  issuer: C=US; O=Amazon; CN=Amazon RSA 2048 M04
  *  expire date: Apr  1 23:59:59 2027 GMT
  ```

🔴 **해설 중 자기정정**: 착수 전 문서에 *"`host:` 를 추가하면 이 우회가 죽는다"* 라고 썼는데
**부정확하다.** `--resolve` 는 Host 헤더를 정상적으로 보내므로 계속 동작한다. `host:` 추가가
없애는 것은 *이 우회*가 아니라 **"아무 Host 로도 접근 가능"** 이라는 성질이다.

## Q1-재확인. *"`--resolve` 는 DNS 를 우회했으니 반쪽짜리 검증"* 주장의 맞는 부분과 틀린 부분

- 사용자 답: *"ALB IP 가 바뀔 때는 제외하고 맞는 말"*
- 정오: △ 부분
- 근거: `0-bootstrap/outputs.tf` `acm_domain_validation` 설명의 Cloudflare **Proxied** 경고

**맞은 것**: 뭔가 남아 있다는 방향. ALB IP 변동을 논점에서 제외한 것도 타당(그건 **재현성** 축).
**놓친 것**
1. *"반쪽짜리"* 는 과소평가 — 서버 측(체인·CN·유효기간·리스너 결선·라우팅·ssl-redirect)은 **전부 증명됐다**
2. 🔴 남은 것의 정체는 **Cloudflare Proxied 모드**. `--resolve` 는 IP 를 직접 박아 **엣지를 건너뛰므로**
   원리적으로 못 잡는다. Proxied 면 브라우저는 우리 ACM 이 아니라 **Cloudflare 엣지 인증서**를 본다
   → 동료 주장은 **결론은 맞고 이유가 틀렸다**. U-11(CORS 가 브라우저에서만 드러남)과 같은 형태

## Q2. `simulate-principal-policy` 첫 시도에서 `learning` 까지 거부된 이유 / 그 결과를 "경계가 지켜졌다"로 읽으면 왜 틀린가

- 사용자 답: 모르겠음
- 정오: ❌ → 교육 후 재확인
- 근거: `infra/aws-eks/2-cluster/irsa-eso.tf:93-101` (와일드카드 없는 정확한 ARN 목록)

**해설 요지**
- Secrets Manager ARN 에는 AWS 가 붙이는 **랜덤 6자**(`-b73fS6`)가 있고 정책은 실제 ARN 을 그대로 쓴다
  (와일드카드 금지 이유가 주석에 있다: 최소권한 + tfsec `aws-iam-no-policy-wildcards` hard fail)
- 내가 만든 `-AbCdEf` 는 어떤 statement 에도 안 맞아 → `implicitDeny`. **이름이 아니라 suffix 때문**
- 판정력 0:
  ```
  가설 A 경계가 이름으로 막는다   → 예측: prod 거부
  가설 B suffix 가 안 맞아 막혔다 → 예측: prod 거부    ← 같다
  ```
- 🔑 **항목 1 의 센티넬 문제 3번째 재발** (#416 라우팅 → 항목 1 볼륨 → 여기)
- 고친 방법도 같은 형태 — **변인 통제**: suffix·리전·계정 고정, **이름만** 교체
  ```
  learning(실제 ARN)  → allowed
  prod(이름만 교체)   → implicitDeny
  ```

## Q4. ACM 갱신 자격이 `ELIGIBLE` ↔ `INELIGIBLE` 로 **되돌아오는** 것이 destroy-after-use 에서 왜 문제인가

- 사용자 답: 모르겠음
- 정오: ❌ → 해설 제공
- 근거: 이 세션 양방향 실측 (`InUseBy: 1 / ELIGIBLE` → `InUseBy: 0 / INELIGIBLE`)

**해설 요지**
- 자동 갱신은 **만료 60일 전**에 시도되고 `InUseBy` 가 비면 `INELIGIBLE`
- 우리 ALB 는 세션 중에만 존재(이번엔 약 4분) → 갱신 시점에 클러스터가 켜져 있을 확률 ≈ 0
- **원인(2026-09)과 결과(2027-04)가 7개월 분리** + 실패 신호 없음(에러·경고·CI 빨간불 전무,
  `INELIGIBLE` 이라는 **정상적으로 생긴 필드값** 하나뿐)
- SOP §9(고아 0)도 §9b(원장 일치)도 **이 필드를 안 본다**
- 내 처음 판단이 틀린 이유: *"붙으면 ELIGIBLE"* 은 사실이지만 그걸 **안심의 근거**로 썼다 —
  **한 방향만 측정하고 결론을 냈다**
- 선택지: ①상시 ALB(월 $23.73, 목적 상충) ②캘린더 감시 ③**재발급 절차화($0 + 2분, 유력)** — 미결정

## Q5. 리퍼(dead man's switch)가 15.8시간 유출을 왜 못 막았나

- 사용자 답: *"마커 자체가 안 생겨서 그런가"*
- 정오: △ 부분
- 근거: `docs/eks-session-sop.md` §안전장치 한계 · `.claude/scripts/eks-reaper.sh:117`

**맞은 것**: 마커는 리퍼의 전제 조건이고, 이번 세션에 실제로 안 만들어졌다(원장 L-58).
**다만 이 사고의 원인은 아니다** — 16:02 에 수동 생성해뒀으므로 destroy 가 돌던 17:22 에는 마커가 있었다.

**실제 이유**
1. **launchd 는 머신이 자면 안 돈다** (SOP §안전장치가 이미 적어둔 한계, *"최악 주말 ~$6"*).
   리퍼는 평가 기회조차 못 얻었다. 확도 🟡 — `pmset` 로 수면 기록은 확정 못 했다
2. 🔑 **더 근본적: 리퍼의 모델에 이 상황이 없다.** 감지 대상은 *"사람이 사라졌다"*(하트비트 2h stale)인데
   17:22 에 나는 활동 중이었고 하트비트는 신선했다 → 리퍼는 **올바르게 아무것도 안 한다.**
   **버그가 아니라 설계 범위 밖**이고, 멈춘 destroy 는 리퍼 눈에 **건강한 세션과 똑같이 생겼다**
- 그래서 교정이 리퍼가 아니라 **절차**였다(하네스 동결 규칙 + 오탐 비용 — 원장 L-59):
  SOP **§5**(apply·destroy 전경 실행 + 마커 육안 확인) · **§8b**(AWS 에 직접 물어 0 확인)
- ***장시간 destroy 를 배경에 두는 것은 dead man's switch 를 우회하는 행위다*** —
  하트비트가 신선한 채로 사람이 손을 떼기 때문

## Q5-재확인. `1/1 Running` 을 근거로 SOP §6b 를 건너뛴 판단이 성립하려면 무엇이 참이어야 하나

- 정오: ✅
