레이어와 스테이지는 1:1이 아니다. 2-cluster 레이어 하나가 클러스터·RDS·시크릿·IRSA를 한 번의 tofu apply로 전부 만든다. RDS를 별도 레이어로 빼지 않은 이유는 자동 정리 장치(리퍼)가 하드코딩된 2-cluster에서만 destroy를 돌리기 때문 — 밖에 두면 사각지대가 되어 영구 과금 위험이 생긴다. “깔끔한 레이어 분리”보다 “안전장치 사정권”을 택한 것.

2 · IRSA — 정적 키 없이 AWS를 부르는 경로

100%

파드가 AWS API를 부르려면 자격증명이 필요하다. 액세스 키를 Secret에 넣으면 정적 크리덴셜이 클러스터에 상주하고, 노드 IAM 역할을 쓰면 같은 노드의 모든 파드가 같은 권한을 갖는다. IRSA는 그 경계를 ServiceAccount 단위로 좁힌다.

Not authorized to perform
sts:AssumeRoleWithWebIdentity		 인증 신뢰정책 sub/aud 불일치.
IRSA 최다 실패 지점
AccessDeniedException …
no identity-based policy allows		 인가 assume는 성공. 권한 정책이 없거나 리소스 ARN이 안 맞는다

후자의 에러 주체는 arn:aws:sts::…:assumed-role/devquest-eks-eso/<세션>으로 찍힌다. assumed-role/로 시작한다는 것 자체가 인증을 통과했다는 증거다. 여기서 신뢰정책을 의심하면 엉뚱한 데를 판다.

권한을 고쳤는데도 계속 실패로 보이면 ESO의 지수 백오프(16s→32s→64s→128s)를 의심한다. kubectl annotate externalsecret <name> force-sync=$(date +%s) --overwrite로 즉시 당길 수 있다.

스크롤 = 확대 · 드래그 = 이동
  • 왜 core-api-db가 두 곳을 읽나 — manage_master_user_password = true로 AWS가 만든 시크릿에는 크리덴셜만 있고 접속 좌표가 없다. host·dbname은 tofu가 따로 만들고 ExternalSecret이 합성한다.
  • 왜 소유자별로 쪼갰나 — 자동 로테이션되는 값(AWS)과 수동 값(우리)을 한 덩어리에 섞으면, Stage 3에서 DB만 in-cluster로 갈아끼울 때 앱 시크릿까지 건드려야 한다.
  • DB_HOST에는 포트가 없다 — jdbc-url이 jdbc:postgresql://${DB_HOST}/${DB_NAME} 형태라 RDS의 .address를 쓴다. .endpoint는 host:5432라 URL이 깨진다.
  • 학습 클러스터에 prod 크리덴셜을 넣지 않는다 — GitHub OAuth·Grafana는 자리표시. 실 크리덴셜을 넣으면 학습 클러스터가 진짜 사용자에게 유효한 토큰을 발급할 수 있게 된다.
